## The rules implemented (quoted from the record)

- MWS-13: "The Approvals page becomes Inbox with two parts. **Needs you**: every pending approval across tasks as the card of MWS-08, mode proposals, and questions. **Updates**: ready for review, a finished child task, an automation's run, a failure, each with its time, a read state and a link that opens its task. Updates are a persisted record kept by the desktop's main process, capped and cleared by the person; an operating-system notification opens the same link."
- Section 7: "PX-206 adds a store in the main process." Section 9: "a destructive effect cannot be allowed from Inbox or home … The updates record holds titles and ids, never transcript text."
- Task card (doc 62): "the record is kept by the main process, capped and cleared by the person; an operating-system notification opens the same link; the list's count stays the Core's attention count." Production wiring: renderer, main ("a capped record under the data directory, list, mark read, clear and open handlers"), preload; "no protocol change".
- QUAL-PX-206: with an approval, a mode proposal and a task ready for review, Needs you decides the first two; Updates shows the third with its time; opening it marks it read; the record survives a restart; the notification's click handler opens its task; the cap holds. Fails if a destructive effect is allowed from Inbox; an update holds transcript text (the record's shape is asserted); a count is taken from the store instead of the Core.

## Existing-code audit (before any edit)

- classification: IMPLEMENTED-PARTIAL. PRODUCTION-WORKING and kept: the Core's attention view (`attention.rs`, `attention:list`), the session's pending approvals (`approvals:dock`), one decision path for an approval with the list rule (`approvals/decide.ts` `decideFromList`, PX-205), the mode proposal's decision (`modeproposals:decide`), the Core's per-task read marker (`MarkRead`, persisted as `ConversationRead` on the task's log, monotonic; headers carry `read_offset`, `last_offset`, `unread`), the derived OS notifications (PX-023 `notifications.ts`, opt-in, quiet hours) and `notify:deliver`.
- What was not there: Inbox listed the Core's attention items as raw text ("CAPACITY · model_concurrency … · StartTask") and a list of derived notifications with "Open review/task"; it decided nothing. No proposals outside their task. No persisted record of updates anywhere (the Core holds no update/notice record; main's `notify:log` is an in-memory list of deliveries). `notify:deliver` showed a `Notification` with no click handler. Inbox's count in the task list was `cols.needsAttention.length`, the renderer store's column (with the Core's attention only as a filter).
- Where the record belongs: the Core was audited first (protocol `stream.proto`, `attention.rs`, `transcript.rs`, `server.rs` MarkRead, `event-store`). The Core already owns the *facts* (task status classes, attention, read markers); it has no record of notices, and the Decision Record decides that the notice record is the main process's ("PX-206 adds a store in the main process"; task card: "no protocol change"). So no protocol or Rust change was made. To stay off doc 81's single owners, the record is a log of notices only: it is written by main from the Core's agent headers (never from a renderer call), holds ids, kind, title, time and the Core offset it is about, and does **not** store a read state of its own: read is the Core's read marker for the task (an update is read once the task's `read_offset` reaches the update's offset), and opening an update moves that marker through the existing `MarkRead`. There is therefore no second read-state owner, and the record's read state agrees with the task list's unread dot.
- first missing link: nothing recorded what happened to a task while the person was elsewhere (no notice record with a time), and the OS notification had no click handler; Needs you had no data for proposals across tasks and no in-place decisions.

## What was built

- **The record (`src/main/inbox-record.ts`, new).** `UpdatesRecord` under the data directory (`inbox-updates.json`, written whole to a temporary file and renamed, mode 0600). Kinds from the Core's status class: `READY_FOR_REVIEW` (ready for review, either seen state), `CHILD_FINISHED` (a subagent's task ready or completed), `AUTOMATION_RAN` (an automation's task ready or completed), `FAILED`. A state is noticed once per task; leaving it and coming back is a new notice; what each task was last noticed for is persisted, so a restart does not notice it again and a cleared notice does not come back. Entry shape, exactly: `id`, `kind`, `taskId`, `title` (the header's title, cut at 120 characters), `atMs` (the header's `updated_at`), `offset` (the header's `last_offset`). Read back field by field: anything else in the file is dropped. Cap: 200 (the record names no number; 200 is `notify:log`'s cap), oldest first out.
- **Main (`src/main/main.ts`).** The record is noted from `GetAgentHeaders` (archived included) 250 ms after a Core event for a task passes main (any page), and when the Core connects again. Handlers: `inbox:updates` (reads the headers, notes them, returns the entries newest first with the Core's read state), `inbox:markRead` (an update id of 32 hex; moves the Core's read marker for its task to its offset, lease taken as the other commands do), `inbox:markAllRead`, `inbox:clear`. Event `inbox:changed` when an entry was added. `notify:deliver` now keeps the shown `Notification` (last 20) and gives it a click handler: the window is restored and focused and `notify:open` names the task (`task:<id>`) or Inbox (a burst).
- **Preload.** `inboxUpdates`, `markUpdateRead`, `markAllUpdatesRead`, `clearUpdates`, `onInboxChanged`, `onNotificationOpen` (re-validates the task id). The PX-049 preload pin is updated with its review note (`hardening-guard.test.ts`). None of the channels is open to a pane window (PX-203's allow list is unchanged). No renderer call can add an entry.
- **Inbox (`renderer/approvals/inbox.tsx`, rewritten; `inbox-model.ts`, `use-inbox.ts` new).** A head at the bar's height (`--mb-top-bar`): the view switch Needs you · N / Updates · N / All, Mark all read (disabled with its reason when every update is read) and Notification settings (Settings at the notification preferences). One centred column (`--mb-column`).
  - Needs you: each pending approval of the session as a card: the question in words ("Run this command?"), the task's title (opens the task), the effect in words ("Protected change", "Cannot be undone"), the exact command, why it asks; Skip and Allow once through `decideFromList(…, "inbox")`, bound to the intent hash shown. What a list may not decide shows its reason and Open to decide. Then each pending mode proposal across the session's live tasks (read from the Core about once a second while Inbox is open; the Core gives 15 s): "Switch to Agent mode?", the task, the agent's words quoted, the seconds left, Keep <mode> and Switch through `decideProposal` (the dock now uses it too: one answer path). Then every other item the Core lists, in plain words (`attentionWords`), opening its task. Approvals are not repeated from the attention list.
  - Updates: rows with the kind in words ("Ready to review", "Child task finished", "Automation ran", "Task failed"), the task's title, a short time ("now", "14m", "6h", "Yesterday", a date; the full time in the title and the accessible name) and a read dot; opening one marks it read through the Core, then opens its task. Clear asks once, inline.
  - Counts: one number, computed once (`approvals/use-needs-you.ts`, `needsYouCount`), is both the task list's Inbox badge and "Needs you · N", and it is the number of rows Needs you draws (see the owner's review below). Updates counts main's record.
- **Notification click (`state/use-app.ts`).** `onNotificationOpen` opens the task (closing a review over it) or Inbox.
- **Styles (`styles.ts`).** Inbox's rules use tokens only (no font size in px; `measured-css.test.ts` passes).

No protocol, Core, Rust, CSP or `webPreferences` change. No locked file changed (no `docs/` or `graph/` edit), so no Decision-Record trailer was required for a locked file; commits carry DR-021's trailer as asked.
