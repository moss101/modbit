# Task Card — IMP-EV-0126 Headless mode

## Identity

- Task ID: IMP-EV-0126 (owner label CLI/API Surface; subsystem domain-events)
- Milestone: M10 Release candidate hardening; prerequisite M9 (COMPLETE)
- Requirements: REQ-EV-0126 (same Core/Policy/Evidence contracts without UI-only tools); QUAL-EV-0126 (an identical task run via desktop and headless yields the same canonical states); docs/29 "thin clients of the same authenticated SurfaceProtocol"; docs/30 "ProtocolCapabilitySet" (REQ-EV-0043); docs/11 §"Input steering is also promoted to a Core contract … used by desktop/web/headless clients"; docs/10 "interchangeable thin clients of one Core"; docs/77 stage 3 row (audit before adding anything, close only the missing links).
- Qualification: real-system — the real `modbit-core` binary, the real `modbit-cli` binary and a real Desktop-kind SurfaceProtocol client against one Core, on real Git fixture repositories, against a scripted OpenAI-compatible provider over real HTTP.
- Evidence tier: release-critical (client authority boundary, policy and evidence contracts).
- No new canonical owner: the CLI stays a thin client (`apps/cli`, owner `desktop`, `canonical = []`). Every verb added carries an existing Core command; no orchestration, policy, Git, recovery or tool code enters the CLI.

## Goal

A person or a CI job driving Modbit headlessly reaches the same Core, Policy and Evidence contracts as the desktop app, with exactly two declared differences: the UI-only surfaces the CLI's ProtocolCapabilitySet withholds, and the provenance that records which surface acted.

## Existing-code audit

- classification: **IMPLEMENTED-PARTIAL**. `apps/cli` is a real thin client — it spawns or attaches to a real Core through `<data-dir>/core.ready`, speaks the authenticated local SurfaceProtocol, presents the session lease generation on every mutation, prints JSON event lines by cursor and sets documented exit codes; `QUAL-PX-000` (`apps/cli/tests/headless.rs`) already drives a whole task lifecycle through it — question, protected-effect approval, Core killed and the stream resumed by cursor, one effect receipt — and a static dependency check keeps provider, fs, git and policy code out of the crate. The withholding half of REQ-EV-0126 is built and proven elsewhere: `client_capabilities` in `services/modbit-core/src/server.rs` gives CLI everything but `ui.selection`, `ui.code_view` and `browser.host`, a command outside the set is refused `CLIENT_CAPABILITY` at the transport before the Core looks at the task, and `qual_ev_0043_a_headless_client_lacks_ui_only_capabilities_while_the_task_stays_valid` pins it.
- method: the Core's `HelloAck.supported_command_types` (71 commands) compared against the command types the headless CLI issues (`apps/cli/src/main.rs`) and against those the desktop and IDE adapters can issue through the TypeScript client (`packages/ide-adapter-core/src/client.ts`, 49) — the desktop's own code names no command type directly; it calls that client.
- **first missing link: `QueueInput`.** Input steering is a Core contract docs/11 promotes for "desktop/web/headless clients" alike, the desktop drives it from the keyboard (`apps/desktop/src/main/main.ts` `task:steer`, PX-024), and the headless CLI has no verb for it at all — a headless operator cannot steer, collect or follow up on a running task.
- the rest of the desktop-reachable, headless-unreachable set, each a real contract the CLI withheld for no stated reason: `TrustRepository` (the CLI holds `repository.trust` and could not use it, so a repository's hooks are never in force for a headless task — `services/modbit-core/src/hooks.rs` refuses them until the session trusts the root: an *identical* task therefore did **not** reach identical canonical states); `ConfigureProvider` (the CLI holds `provider.configure` and could not use it — headless configuration was environment variables only); `GetRecoveryReport` (the crash-recovery evidence the desktop shows after a restart); `OpenPullRequest` / `UpdatePullRequest` (the reviewed candidate's forge path); `ListStarterTasks` (the detected stacks and the session's trust of the root).
- intended differences, asserted rather than closed: `GetCodeView` needs `ui.code_view`, which the CLI's ProtocolCapabilitySet withholds — it is refused `CLIENT_CAPABILITY` and the task named stays valid; `SubmitExternalDiagnostics` is the IDE adapter's, and what it submits is tagged `provenance=external_ide` (docs/29).
- not a parity gap, recorded and left with their owners: `ExportHandoff` (IMP-EV-0142 trace/status/export diagnostics), `IngestCiResults` (PX-009), `ReadObjectRange` (REQ-EV-0108 OutputRef paging), `GetEffectivePolicy`, `CompensateEffect`, `AskSideQuestion`, the routing and model-registry operations, the cloud/worker operations (`ConfigureSandboxGateway`, `AdmitReviewEnvironment`, `DisposeReviewEnvironment`, `ImportObjects`, `ReconcileUsage`, `MaterializeOutcomeStatistics`, `RebindTaskWorkspace`), `ConfigureForge`, `IngestReviewComments` and the external-tool management commands (M9.4). (`SubscribeEvents` is not among them: both surfaces reach it through their client's `subscribe` helper — `events tail` is the CLI's.) Neither the desktop nor the CLI drives any of the rest, so none is a difference between the two surfaces; each belongs to its own task.

## Change

- `apps/cli`: six verbs over existing Core commands — `task steer` (`QueueInput`, `--mode STEER|COLLECT|FOLLOW_UP`), `workspace trust` (`TrustRepository`), `provider configure` (`ConfigureProvider`), `recovery show` (`GetRecoveryReport`), `pr open` / `pr update` (`OpenPullRequest` / `UpdatePullRequest`), `starter list` (`ListStarterTasks`).
- **Credential custody:** `provider configure` never takes the key as an argument — argv is world-readable in the process table. The key is read from `MODBIT_PROVIDER_API_KEY` or from stdin, is not echoed, is not written to the CLI's output, and what the CLI prints is the Core's `ProviderConfigured` (endpoint, whether a credential is available, the models) and never the value.

## Verification

- `qual_ev_0126_an_identical_task_runs_the_same_through_the_desktop_client_and_the_headless_cli` (`apps/cli/tests/headless.rs`): one real `modbit-core`, two byte-identical fixture repositories that each declare the same repository hook in their Project configuration layer, one scripted OpenAI-compatible provider over real HTTP, and the same task run twice — once by a `DESKTOP` SurfaceProtocol client, once by the real `modbit-cli` binary across separate processes — through a plan that declares a protected effect, a typed question answered from the shell, a queued `FOLLOW_UP` line, a workspace change, `git.worktree.create`, the Destructive `git.worktree.close` approved from another shell while the run holds, verification, and an accepted review. The two runs' ordered canonical task-event sequences are compared and are equal, including `HooksResolved` / `HookInvoked` on both runs, `TaskInputQueued` / `TaskSteered`, the approval ladder (`ToolCallApprovalRequested`, `ApprovalRequested`, `TaskWaiting`, `ApprovalResolved`, `TaskResumed`, `EffectReceiptAppended`), `RealizedRiskDerived` / `AcceptanceGateEvaluated` and `TaskCompleted`; so are the final state, the effect receipt (`SUCCESS` under an approval; the approval's id is normalized away, being an identifier and not a canonical state) and the review outcome.
- the declared differences, asserted in the same test: `CreateTask.origin` records `cli` for the headless run; `GetCodeView` from a headless connection is refused `CLIENT_CAPABILITY` (the Core naming the nine capabilities a CLI client does hold) and the task it named is still `Completed` afterwards.
- the contracts the task made reachable headlessly, exercised against the same Core: `task steer` (inside the parity comparison), `recovery show`, `starter list`, and `pr open` refusing a stale `--revision` before anything reaches a forge.
- credential custody: `provider configure` with the key in `MODBIT_PROVIDER_API_KEY` returns `credential=available`; the key appears in neither stdout nor stderr; the same command with `--api-key` is refused with "a credential never goes on the command line"; and a byte scan of every file under the data directory finds the value nowhere.
- failure injection: removing the headless `workspace trust` fails the comparison on the two `HookInvoked` events the desktop run has and the headless one does not — the exact defect REQ-EV-0126 forbids; removing `task steer` fails it on `TaskInputQueued` and `TaskSteered`. Both were run and both failed as required.
- regression: the CLI's four existing qualifications (`qual_px_000_headless_cli_task_lifecycle`, `qual_ev_0111_0268_…`, `qual_ev_0181_0210_…`, `cli_drives_a_real_core_end_to_end`) still pass. `modbit-cli` still links no provider, filesystem, Git, policy, tool, runtime, event-store, terminal, sandbox, effects or secrets crate — PX-001's `scanCargoClosure` is unchanged and the new verbs add no dependency.

## Limitations

- The parity proof is one task shape. It covers a plan, a typed question, steering, a workspace change, a protected effect with an approval and a receipt, verification and an accepted review under `local_trusted`; it does not compare a cancelled task, a returned review, a crash mid-run (`qual_px_000` covers the headless half of that), a `cloud_isolated` task, or a browser task — the desktop hosts the browser and a headless client cannot, which is the withheld `browser.host` capability, not a parity gap.
- `pr open` / `pr update` are proven only to the point where the Core refuses a stale candidate revision; the forge path itself is PX-006's qualification, which uses a fake forge in the Core's own suite.
- `provider configure` reads the credential from stdin when `MODBIT_PROVIDER_API_KEY` is absent, so it blocks on a terminal with no input; that is the documented headless contract (pipe it), not an interactive prompt.
- The commands neither surface drives are recorded in the audit above and left with their owners; `ExportHandoff` (IMP-EV-0142), `IngestCiResults` (PX-009) and `ReadObjectRange` (REQ-EV-0108 OutputRef paging) are the ones a headless operator is most likely to want next, and none of them is a difference between the desktop and the CLI today.
