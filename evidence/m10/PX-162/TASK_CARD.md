# PX-162 task card — rule, skill and memory changes arrive as appended transcript notes

Decision Record: DR-PX-2026-10-26-018 (D1, D2). Evidence tier: release-critical (it changes what the model is told, persistence of the transcript and the prompt prefix).

## Audit (before)
Classification: IMPLEMENTED-PARTIAL / BROKEN-DRIFTED against the requirement. `services/modbit-core/src/runtime.rs` re-ran `rules.select`, `RunSkills::turn` and `memory::select_for_prompt` every turn and fed the results straight into `modbit_prompt_compiler::compile`. An edit to AGENTS.md, a lazily activated nested rule, a skill change or a promoted/edited memory therefore rewrote the system segments or the task turn, so the provider's cached prefix was invalidated mid-task (the compiler's own comment called a memory change "a deliberate new prefix"). Two PX-107 tests pinned that behaviour. First missing link: nothing remembered what the prefix was compiled from.

## Change
- `services/modbit-core/src/instruction_delta.rs` (new): `Tracker` keeps the `Instructions` (rule texts, skill texts, memory fragments) the prefix was compiled from and what the model has been told since. Per turn: first request or a new compaction epoch → the prefix is compiled from the current instructions; otherwise additions and replacements (same rule/skill header, or a memory edit that retires an item and puts a new one in its scope/type/topic slot) produce one `Note` (what changed, what it replaces with both hashes, the current text with its own provenance header, bounded to 8000 characters per item) and the prefix inputs stay as they were; anything that is only taken away (forgotten/expired memory, revoked skill, removed rule file) rebuilds the prefix from the current instructions, because withdrawn text must leave the request.
- `runtime.rs`: the compile step passes the tracker's `base` instructions to `compile`; a note is recorded as the `InstructionUpdateNoted` event (aggregate: the task's Workspace records) and pushed on the transcript as a user message; a deliberate rebuild after the first request is recorded as `InstructionPrefixRebuilt` with its reason (`COMPACTION_EPOCH` or `WITHDRAWN`); `rebuild` replays `InstructionUpdateNoted` into the transcript like the other delivered notices (`HunkNoticeDelivered`, `AutoVerificationDelivered`).
- Untrusted repositories are unchanged: `rules.select` already loads nothing from them, so there is nothing to note.
- `context_rules_pack.rs`: the two PX-107 tests that asserted a rewritten system segment now assert the byte-identical prefix and the appended note (a requirement change recorded in DR-PX-2026-10-26-018, not a weakened assertion: each still checks provenance, the hash, order of the edit and that the new text reaches the model).

## Proof
`services/modbit-core/tests/memory_graph_index.rs`, real Core process, real git repository, real SQLite store, real memory commands (ProposeMemory/PromoteMemory/EditMemory/ForgetMemory over the protocol), scripted OpenAI-compatible model whose reply is held while the test edits:
1. `qual_px_162_a_changed_rule_file_and_memory_arrive_as_one_note_and_the_prefix_stays`: AGENTS.md and a memory item change while the model composes its second answer. Every request of the run has byte-identical prefix (system segments + task turn, holding RULE-V1/MEM-V1); no note before the change; exactly one note after, in every later request; the note names both changes, what each replaces (the retired memory's short id and the rule header), both carry provenance; a task started afterwards reads RULE-V2/MEM-V2 in its fresh prefix and the running task read the same text as prefix + note; one `InstructionUpdateNoted` event, no rebuild.
2. `qual_px_162_a_resume_rebuilds_the_same_note_from_the_log`: SIGKILL the Core while the third request is held, start a new Core on the same data, StartTask: the resumed request carries the identical note text, rebuilt from the log, and a freshly compiled prefix that already holds the change.
3. `qual_px_162_a_forgotten_memory_rebuilds_the_prefix_and_an_untrusted_file_adds_no_note`: a forgotten memory is absent from every later request and one `InstructionPrefixRebuilt` is on the log; an AGENTS.md edit with an injection-shaped sentence in an untrusted repository adds no note and no text.
Unit tests: `instruction_delta::tests` (edit + new memory = one note and base unchanged; withdrawal and compaction epoch rebuild; memory edit replaces within its slot). Mutation: `evidence/m10/PX-162/mutation-check.txt` (the tracker always rebuilds → tests 1 and 2 fail).

## Known limits
- A replaced item's old text stays in the cached prefix; the note says it is superseded. A model could in principle follow the older text; the prefix is rebuilt at the next compaction epoch or new task.
- A removal is never a note. The prefix is rebuilt at that turn (a deliberate, logged cache miss) because withdrawn memory or a revoked skill must not remain in the request.
- Items are matched by their header (rule/skill) or id (memory); a rule whose id changes is a removal plus an addition and therefore a rebuild.
- The completion gate refuses a task whose workspace the test edited, so the tests stop at the requests rather than completing the task.
