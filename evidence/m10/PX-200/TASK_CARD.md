## Existing-code audit (before any edit)

- classification: IMPLEMENTED-PARTIAL for the task view; NOT-FOUND for the plan's bridge. Traced from the production caller to the Core: `Shell` mounts `TopBar` and `Conversation`; `useConversation` reads `GetTranscript` and re-reads on the task's events; `RowView` draws the Core's rows; `Composer` reads the Core's posture and queue; `ApprovalDock` reads `ListDockApprovals` and makes the typed decisions; every effect is a preload call main validates. All of that worked and is kept.
- first missing link: no client, IPC or preload method for `GetWorkGraph` or `GetPlan` (the Core serves both, `server.rs`; only the CLI called them). The renderer said "Updated the plan" from transcript rows whose tool name starts with `plan.`.
- **Do all plans reach the work graph as steps? No.** Read in `services/modbit-core/src/runtime.rs` (`handle_plan`): a `plan.update` call records `PlanRecorded` or `PlanRevised` always, and `WorkNodesChanged` only when its `steps` changed a node. `steps` is optional in the tool's schema (`required: ["outcome", "expected_files"]`), so a plan that names no steps is a plan version and a transcript row with no node in the graph. Shown on the real Core by `e2e/px-200-task-view.spec.ts` (second test): after such a plan `workGraph` has 0 steps while `plan` reports version 1 with its outcome. `e2e/awl.spec.ts` has run such a plan since PX-194. So the card is drawn only where the graph has steps, and a task without steps keeps its plan line as before.
- Three more facts from the same read. A step changes state only when the agent says so in a later `plan.update` (DONE needs an evidence reference and done dependencies, or the whole change is refused), or when a subtask is admitted against a node (`spawn.rs`, `WorkNodesChanged` with no plan version): nothing moves a step by itself. The transcript's plan row carries the plan's outcome only, never a step. A person's `RevisePlan` (`plans.rs`) validates steps against the graph but appends no `WorkNodesChanged`; the desktop does not call it, and it is noted here only because it is a second way a plan with steps would not reach the projection.
- the approval card: a form of two native selects (prefix, scope) and five controls in its foot; the tool's name in the headline; the intent hash, the arguments (a `details`, so out of the accessibility tree while closed) and the run mode in the open. The composer: two rows (text, then a bar of mode, model, add context, ring, stop, send) and a foot with the location and the run mode. The top bar: title, state, branch, the details overflow and one "Apps panel" toggle shown only while the panel was closed.
- The Core has no command to rename a task (`AgentHeader.title` is the goal's text; projects can be renamed, tasks cannot). The title's menu therefore has no Rename.

## What was built

- **Bridge (the two reads).** `CoreClient.getWorkGraph` and `getPlan` (`packages/ide-adapter-core`); main's `conversation:workGraph` and `conversation:plan` (`conversation-ipc.ts`: a validated task id in, plain data out, no lease); preload `workGraph(taskId)` and `plan(taskId)`. No protocol, CSP or Rust change. The preload pin in `hardening-guard.test.ts` moved with a comment naming this row; the two names are in `e2e/workers.spec.ts`'s allow-list.
- **Plan card (MWS-06).** `conversation/use-plan.ts` reads both whenever the transcript's last offset moves (every task event re-reads the transcript, so a graph change with no plan row is followed too). `conversation/plan-card.tsx` lists the graph's steps in the graph's order with the Core's state as a glyph and words, the plan's outcome, "n of m done" and how often it was revised. It stands where the latest plan version was recorded; every plan step leaves the transcript, alone or inside a fold, and a fold that held only plan steps goes with them (`withPlanCard`, pure, unit-tested). An ACTIVE step spins only while the turn runs; while the task waits on the person it says "In progress, waiting for you".
- **Transcript text (MWS-06).** Steps, folds and the status line are at the transcript's size (15 on 21, 14 on 20 in Compact); they were at the chrome's.
- **Status line (MWS-06).** What runs (the Core's tail label with the stall ladder, unchanged), then for how long and the tokens used: the time since the person's latest message that has work after it (a message that is only queued does not restart it), ticking while the task runs or waits on the person; the tokens are the Core's count for the task (`GetTaskEconomics`, input plus output). The clock is outside the live region, so it is not read out every second.
- **Composer (MWS-07).** One box: add context (the same menu, a plus), the text, then stop or send. The text area is one line and grows with its content to 40 % of the window's height. While a turn runs and nothing is typed only Stop stands there; with text there is also the send that queues, as before. Under the box: where the task runs at the left (it stays until the details rail takes it); at the right the mode chip (the board does not draw it; it is kept reachable there), the model, the run mode (a shield and the mode's name; "Run mode:" is in its accessible name) and the context ring. Each opens what it opened. The conversation reads the accounting once and feeds both the ring and the status line.
- **Queue tray (MWS-07).** Each queued message is one filled strip above the box: the message, how it will run, Send now, Remove. Edit (the strip itself or the pencil) and, with two or more queued, the two move buttons stay beside them, as do the count, Clear and Collapse (PX-055's behaviour).
- **Approval card (MWS-08).** The headline says what will happen in words ("Run a command?") with the effect class as a tag; then the exact command, the paths, hosts and always-ask classes where there are any, and why the Core asked, with Change run mode beside it; then one disclosure, "Exact arguments and intent", holding the tool's name, the intent hash, the working directory, the effect and sandboxing, the run mode and the arguments. Closed, that content is clipped from sight and stays in the accessibility tree. The foot is Skip, Always allow, Allow once. Always allow opens one menu: the prefix (every prefix of the command, the exact command chosen, each with what it would cover), where the rule applies (this repository for 30 days, or this task) and Allow and run. Enter, Shift+Enter (allows the chosen prefix), Escape and the confirmation rule are `cardKey`, unchanged; Escape with the menu open closes the menu and nothing else (a layer). An irreversible or always-ask effect shows no Always allow, says why, and asks twice.
- **Title bar (MWS-05).** The title opens the task's menu: Pin or Unpin, and Archive (through the task list, which owns pins, the confirmation for a running task and the undo). One toggle per pane the task can show (Changes, Terminal when the Core lists one, Browser, Files, Evidence), each pressed while the panel shows that pane; a click opens the panel on it or closes it. Then More (the task's details, `task-details-toggle`). The state pill and the branch stay.
- **Removed in the same change:** the two selects and their labels; the `details` for the arguments; the tool's name in the headline; the two-row composer's bar (`.cmp-row`, the bar inside the box) and the 44 px text area in a task; the single "Apps panel" toggle of the top bar with its disabled state, and `IconPanel`; the card's container query that hid key hints when narrow (the foot now fits).

## Limitations

- **"The graph changes with no plan line and the card must follow"** is not shown with such a change. On the real Core every node change the test can cause arrives with a plan version (a `plan.update`); the one path without (a subtask admitted against a node, `spawn.rs`) is not scripted. What is shown instead: the card equals `workGraph` at every stage, it is re-read on the transcript's offset (which every task event moves), and the transcript holds no step title or state, so a card fed from it could not pass.
- BLOCKED, FAILED, CANCELLED and READY steps, and a step with blockers, are unit-proven only (`planSteps`); the e2e run reaches PENDING, ACTIVE and DONE.
- "Send now" in the tray and Archive in the title's menu are asserted present, not exercised here (`composer.spec.ts` and `agents.spec.ts` exercise the same functions from their old places). Pin is exercised.
- The Always allow menu is placed with CSS anchor positioning; it was looked at over a card at the foot of a 900 px window, not in a short window where it would have to flip.
- The status line's elapsed time was looked at for seconds only; minutes and hours are unit-proven.
- **CI run 1** (43167558623 on f4dbb1f7, pull request 199): every job passed but the three desktop E2E jobs, each with one failure, a different test on each system: macOS 203 passed, 1 failed (`task-list.spec.ts:492`); Ubuntu 203 passed, 1 failed (`context.spec.ts:45`); Windows 199 passed, 1 failed, 6 skipped (`task-list.spec.ts:492`, at another line).
