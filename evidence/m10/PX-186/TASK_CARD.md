# PX-186 task card — memory retrieval ranking with recency, importance and diversity, kept only if it beats the current ranking

Decision Record: DR-PX-2026-10-26-018 (D1, D2). Evidence tier: release-critical (the row changes how the Core selects prompt memory). Prerequisites PX-184 and DOC-PX-017 are COMPLETE.

**Outcome: REVERT.** The candidate ranking recalled less than the current one at the same token budget. The scoring change is reverted; the comparison harness, the corpus, the ranking record and the negative result are kept.

## Audit (before)
Classification: IMPLEMENTED-PARTIAL for the ranking, NOT-FOUND for the comparison. `MemoryStore::select` (`crates/memory/src/lib.rs`) scored keyword relevance 0.5, scope precedence 0.2, confidence 0.2, validated or user-stated 0.1, as the row's audit says; the Core (`services/modbit-core/src/memory.rs` `select_for_prompt`, called each turn from `runtime.rs`) packed the selection under the 800-token memory segment (`PROMPT_MEMORY_BUDGET_TOKENS`) and kept a memory record with the ContextCompile step. Nothing named the ranking in that record, and nothing could run two rankings through one Core. The PX-184 memory axis seeds one item per task (`suites/four-axis/tasks.json`), so any ranking scores 10/10 there and a comparison on it measures nothing.
First missing link: a memory-axis measurement in which ranking decides what reaches the prompt under a fixed budget, and a recorded, switchable ranking the real Core runs.

## Change
Two code commits on `wip/px-186-memory-ranking`:

1. `fc2294a2` (measurement state). `crates/memory`: `SelectionInput.ranking` and `Selection.ranking`; `Ranking` with `version()`, `weights()` and `record()`; the current score as `keyword-v1` (the default) and the candidate `recency-importance-diversity-v2`: relevance 0.4, precedence 0.15, confidence 0.15, validated 0.1, recency 0.1 (half-life of 8 newer in-scope items, counted in items so the score never reads the clock), importance 0.1 by record type (failure pattern 1.0, decision and preference 0.8, convention 0.7, procedure 0.6, dependency 0.5, fact 0.4), and a greedy diversity penalty of 0.3 times the largest word overlap (Jaccard) with an item already taken (items of one conflict never penalise each other). The Core selects with the ranking `MODBIT_MEMORY_RANKING` names (unset or unknown: the default) and the prompt's memory record carries `ranking: {version, weights}`; `memory.query` uses the same ranking. `benchmarks/agent-engineering`: `src/ranking.rs` (corpus, observation from the Core's records, `compare_rankings` with its refusals and keep rule), `competence-baseline memory-ranking` (`src/bin/competence_baseline/memory_ranking.rs`), `suites/memory-ranking/corpus.json`.
2. `fa400c20` (revert). The candidate's terms are removed; `keyword-v1` is the only ranking and the default, and its score is computed exactly as before (the same four products added in the same order). Kept: the ranking record, the environment switch (so the next candidate is compared the same way), the harness (the candidate is now a required argument), the corpus and the retained comparison `benchmarks/agent-engineering/baselines/memory-ranking/` (`comparison.json`, `passes.json`, `summary.md`).

### The comparison tasks (designed before either ranking was measured; not tuned afterwards)
`suites/memory-ranking/corpus.json`: one team's curated memory for the PX-184 `inventory` fixture, 42 items seeded through the CLI (`memory propose|promote`) in a fixed order that is the history, and 12 tasks whose goals need named items (16 gold groups). A gold group is items that carry the same information (paraphrases); it is recalled when any one of them reaches the first prompt. The store holds what a team's memory accumulates: three paraphrases of the deploy procedure and two of the upload-test command; a corrected staging port beside three notes of the retired one; a carried conflict (`api version` v3 and v4); standing conventions and preferences that are candidates for every task; words shared by unrelated items; two sensitive session notes that share the tasks' words; one repository fact validated before the repository's revision moves. Gold is spread across the history (of the 16 groups, 9 only in the older half, 5 only in the newer half, 2 in either) and across types (convention 6, failure pattern 4, procedure 4, fact 2, decision 1, dependency 1, preference 1). Each task's `why` in the corpus says why its gold is its gold.

### The harness
Five passes, one after another, each a fresh Core profile and a fresh copy of the fixture at one path of exactly 120 bytes (repository items' headers carry the path, so its length is part of each item's token cost; the same path also gives the same content-addressed ids, so a ranking that breaks ties by id breaks them alike in every pass): the Core's default (no ranking named), the current ranking, the candidate, and each of those again. Each task is created and run for one turn with a scripted model that answers with one line of text (the measurement is of the prompt the Core builds, never of the model). From the Core's own records: the ContextCompile step's stored output (`memory.ranking`, `memory.token_budget`, `memory.token_used`, `injected_memory`) and the turn's `MemoryUsed` events. `compare_rankings` refuses a task without a record, a record naming another ranking than its pass asked for, tokens over budget, an item that is no corpus item, a record that disagrees with `MemoryUsed`, a sensitive or stale item offered, a ranking whose two passes differ, unequal budgets between the rankings, one ranking compared with itself, and a product default that is not the ranking the decision keeps. Keep rule: the candidate recalls more gold groups at the same budget and its recall per thousand injected tokens is not lower.

## Proof
Comparison (retained; `benchmarks/agent-engineering/baselines/memory-ranking/comparison.json`, environment: revision fc2294a2, build digest `361ec61e…`, macos-aarch64):

| ranking | gold groups recalled | recall | injected tokens | budget tokens | recall per 1k tokens |
|---|---|---|---|---|---|
| `keyword-v1` (current) | 16/16 | 1.000 | 9058 | 9600 | 1.766 |
| `recency-importance-diversity-v2` (candidate) | 14/16 | 0.875 | 9078 | 9600 | 1.542 |

Every task ran at 800 tokens under both rankings; both rankings reproduced every task's injected items and tokens on an independent profile; no sensitive or stale item reached a prompt under either; the Core's default was `keyword-v1`. Decision: **revert**. The two losses: `deploy` (the candidate took the newer rollback procedure, then penalised all three deploy paraphrases for their overlap with it, so none fit) and `release-prep` (importance and recency lifted a failure pattern and newer items whose only overlap with the goal is a substring such as "out", and the oldest item, the changelog convention, fell out of the budget). With relevance down from 0.5 to 0.4, query-independent priors displaced relevant older items.

Stability: the comparison ran three times locally with the candidate present (different process ids, so different workspace paths of the same length): the candidate gave 14/16 and 9078 tokens every time; the current ranking 16/16 every time with 9040, 9004 and 9058 tokens, and 16/16 again in the real-Core test after the revert (ties broken by content-addressed id move which non-gold item fills the last slot). A first run whose passes used different workspace paths was refused as nondeterministic for that reason, which is why every pass now uses one path.

## Known limits
- The comparison's model is scripted; it measures what reaches the prompt (recall at a fixed budget), not whether a live model then uses it. No live model ran (the DR authorizes no live spend).
- The current ranking recalls every gold group of this corpus, so a candidate could at best tie on recall here; the corpus was fixed before measuring and was not made harder afterwards. A future candidate needs a harder corpus version (with its own gold, designed first) to show a gain.
- Injected-token totals of the current ranking vary by tens of tokens across machines (ties are broken by content-addressed id, and the ids follow the workspace path); recall did not vary in four runs. The real-Core test asserts the recall and the decision, not the token total.
- The optional semantic match of the card is out of scope (the embedder has no dependency admission).
- `MODBIT_MEMORY_RANKING` is an operator setting read at Core start; it now names one ranking. An unknown name falls back to the default, and the record says which ran.
- CI has not run this change; the graph stops at REAL_TESTING. Linux and Windows are untested locally (the harness keeps the workspace path at 120 bytes on each and waits for a pass's Core to exit before the next pass reuses the path).
