## Increment 1 — the decision core and the signing tool

- `apps/desktop/src/main/update/manifest.ts`: ed25519 signed manifests (the signed bytes travel as a string, so no canonicalization can disagree); pinned keys with revocation; artifact size and sha256 checked before use; a stable per-install rollout bucket that only widens; `decideUpdate` (channel, newer, device `minimum_version` floor and forced update, staged rollout, `min_supported_version`, database newer than the update refused, database too old refused, a critical migration installed only behind a backup); `planRollback` (newest earlier release that can open the database, from the pre-migration backup when its schema is older, refused when neither holds). `node:crypto` only.
- `tools/release/release.mjs`: `keygen`, `schema-version` (read from the `MIGRATIONS` table, so a manifest cannot drift from the tree), `checksums` (sha256sum format), `manifest` (signs with the secret from the environment), `verify` (signature and artifacts on disk). Signs with the same module the app verifies with.
- Verification: `manifest.test.ts` (real ed25519 and sha256; tamper, wrong key, unknown key, revoked key, malformed payload, artifact tamper, rollout distribution and monotonicity, every refusal reason, rollback cases) and `release-cli.test.ts` (the real CLI as a child process: key refused inside the repo, mode 0600, no overwrite, no key no manifest, the app-side module accepts what the tool signed, every tamper fails with its own code). Both run in `pnpm test` on macOS, Linux and Windows.
- Found by the tests, fixed here: the CLI defaulted `min_supported_version` to the release's own version and `min_db_schema_version` to the current schema, which would have refused every older install and every earlier database.

## Increment 2 — packaging, the update client, the helper (2026-10-02)

- Decision Record `DR-M10-2-2026-10-02` (this directory): electron-builder for packaging, CycloneDX for SBOMs; one recorded deviation (pnpm's native `pnpm sbom` replaces `cyclonedx-npm`, which cannot read pnpm's layout).
- First missing link found while packaging: a packaged app looked for `modbit-core` under a checkout's `target/debug`. The package now carries the release `modbit-core` and `modbit-execd` in its resources (the Core finds execd as a sibling), `main.ts` resolves them from `process.resourcesPath` when packaged, and a Playwright test launches the real packaged executable with no `MODBIT_CORE_BIN`; removing the bundled Core makes it fail.
- `modbit-core` offline subcommands, read-only and runnable beside a Core: `schema-info` (build and on-disk schema, never migrates, never creates `core.db`), `backup` (`VACUUM INTO` a consistent single file, refuses to overwrite) and `device-policy` (the device constraints read the way the Core's own `GetEffectivePolicy` reads them). The desktop never opens the Core database. Proven by `crates/event-store/tests/update_schema.rs` and `services/modbit-core/tests/update_cli.rs` against real SQLite and the real binary.
- `client.ts`: fetch the signed manifest, verify against pinned keys, `decideUpdate`, download, size and sha256 against the signed manifest, backup before a critical migration, stage; `.part` files are discarded at start; the staged file is verified again from disk before use. Rollback fetches the earlier release's own signed manifest (`releases/<version>/manifest.json`) rather than trusting a local copy. `client.test.ts` runs it against a real HTTP feed.
- `apply-helper.ts`: the Electron binary as plain Node waits for the app to exit, optionally restores the pre-migration database (keeping the post-update one), swaps the bundle and puts the old one back if the new one cannot be installed, writes `apply-result.json`. A bundle whose own `CFBundleShortVersionString` is not the version the manifest promised is refused.
- Packaged E2E on macOS (`e2e/packaged-update.spec.ts`): a keyless build offers nothing and never asks the feed; hostile feeds each refused with their own code (digest, size, tampered manifest, unknown key, rollout hold, database too old, database newer than the update); the device minimum read from the Core; a real SIGKILL mid-download leaves nothing that looks verified and the next check succeeds; an install that cannot complete leaves the old app intact and says why; a real update to 0.0.2, the new version running on the same profile, and a rollback to 0.0.1. Verified non-vacuous: with digest verification mutated off, the hostile-feed test fails.
- A found hazard, stated: the macOS swap is two renames; a kill of the helper between them would leave no app. The window is microseconds and not covered by a test.

## Increment 3 — SBOM, license gate, reproducibility (2026-10-02)

- `release.mjs sbom`: CycloneDX 1.5 for `modbit-core` (412 components) and `modbit-execd` (99) from `cargo-cyclonedx`, and the desktop from `pnpm sbom` plus an explicit Electron runtime component; each checked to be CycloneDX with named, versioned components. `release.mjs verify --sbom-dir` checks every SBOM against the digest the signed manifest carries, so a swapped or missing SBOM fails.
- `release.mjs licenses` with `tools/release/license-policy.json`: permissive allowed, copyleft and unknown refused until a review is recorded; first-party packages are recognised from the workspace (a third-party `UNLICENSED` crate fails). The real SBOMs pass with no exceptions. `sbom-cli.test.ts` covers GPL, AGPL-in-AND, unknown, undeclared and third-party UNLICENSED failing, OR-alternatives passing, and a tampered SBOM failing `verify`.
- `tools/release/repro.mjs`: two clean builds, same inputs. Result on macOS arm64: desktop bundles identical; Rust binaries were NOT identical until the build path was made identical and remapped (the generated protocol code's `OUT_DIR` was embedded, which also changes the Mach-O UUID). With a fixed, remapped target path both binaries match. Not proven: reproducibility across different checkout paths or machines, and of the packaged zip/dmg/installer themselves.
