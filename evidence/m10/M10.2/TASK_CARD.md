- pinned already (docs/70 reproducibility): `rust-toolchain.toml` (1.97.1), `.node-version` (26.5.1), `packageManager` pnpm 11.8.0, `Cargo.lock`, `pnpm-lock.yaml`, exact versions on Electron (44.3.0) and esbuild (0.28.2).
- migration surface to honor: `crates/event-store/src/schema.rs` `MIGRATIONS` / `SCHEMA_VERSION` (17), and `migrations.rs` refusing a database newer than the build (`Error::SchemaTooNew`). An update that writes an older schema than the database on disk cannot open it; that is what "compatibility checked before install" must catch.
- first missing link: nothing decides, before a byte is installed, whether a downloaded update is authentic, wanted, admitted by its rollout, and able to open the user's database.

## Increment 1 — the decision core and the signing tool (this commit)

- `apps/desktop/src/main/update/manifest.ts`: ed25519 signed manifests (the signed bytes travel as a string, so no canonicalization can disagree); pinned keys with revocation; artifact size and sha256 checked before use; a stable per-install rollout bucket that only widens; `decideUpdate` (channel, newer, device `minimum_version` floor and forced update, staged rollout, `min_supported_version`, database newer than the update refused, database too old refused, a critical migration installed only behind a backup); `planRollback` (newest earlier release that can open the database, from the pre-migration backup when its schema is older, refused when neither holds). `node:crypto` only.
- `tools/release/release.mjs`: `keygen`, `schema-version` (read from the `MIGRATIONS` table, so a manifest cannot drift from the tree), `checksums` (sha256sum format), `manifest` (signs with the secret from the environment), `verify` (signature and artifacts on disk). Signs with the same module the app verifies with.
- Verification: `manifest.test.ts` (real ed25519 and sha256; tamper, wrong key, unknown key, revoked key, malformed payload, artifact tamper, rollout distribution and monotonicity, every refusal reason, rollback cases) and `release-cli.test.ts` (the real CLI as a child process: key refused inside the repo, mode 0600, no overwrite, no key no manifest, the app-side module accepts what the tool signed, every tamper fails with its own code). Both run in `pnpm test` on macOS, Linux and Windows.
- Found by the tests, fixed here: the CLI defaulted `min_supported_version` to the release's own version and `min_db_schema_version` to the current schema, which would have refused every older install and every earlier database.
