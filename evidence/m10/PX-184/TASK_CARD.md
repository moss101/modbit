# PX-184 task card — four-axis agent benchmark

Decision Record: DR-PX-2026-10-26-018 (D1, D2). Evidence tier: iteration (an evaluation suite, its harness and result bundles; no effect, store, policy, protocol or Core behaviour changes).

## Audit (before)
Classification: IMPLEMENTED-PARTIAL. `benchmarks/agent-engineering` had the PX-020 competence harness (real Core, real tools, the headless CLI, scoring from the Core's event log and `task economics`, an immutable bundle) and six coding tasks, as the row's audit says. Nothing tagged a task by axis, no task exercised memory, skills or sub-agents, a task was scored only by acceptance commands, there was no cost-per-thousand figure and no compare or gate. First missing link: a task could not name the capability it measures or a verifier that reads the Core's own records.

## Change
- `src/suite.rs`: a task may carry `axis`, its own `verifier` and `seed` (curated memory, owner-trusted skills); the protocol may carry `run_mode` and `axes` (`min_tasks_per_axis`, `gate.max_drop`). The new fields are skipped when absent, so the internal suite's digest is unchanged (`a6cdf39a…`, the one the PX-020 evidence bundles name).
- `src/verifier.rs` (new): file checks; tool checks against the tool results the Core stored (`ToolCallSucceeded.result_ref` in the profile's object store); memory checks (`MemoryUsed` or a `memory.query` result naming the seeded item's id; a forgotten item reaching the task fails; `MemoryProposed` by an `agent:` author); skill checks (`skill.load` result or `SkillSelected` with the trusted content hash); sub-agent checks (`SubagentAdmitted`, `SubagentResultRecorded`, `MergeTransactionRecorded` `COMMITTED`). Nothing the model says is read.
- `src/axes.rs` (new): suite validation (every task tagged by a known axis, a verifier with an id and checks no other task shares, at least ten tasks per axis — a suite cannot lower that floor — and a gate that can fail); the report (verified success per axis with a 95% Wilson interval; output tokens and USD per thousand tasks from recorded usage only); `verify_against` (a report's figures must be the bundle's); `compare` with the per-axis gate (fails when an axis is more than `max_drop` = 0.05 below the baseline; refuses a gate that cannot fail and reports of different suites).
- `src/bundle.rs`: a trial records `axis`, its `verifier` verdict (part of `acceptance_passed`) and `usage` (economics of the task and every child it admitted, beside the `ModelUsageRecorded` events of the trial's log).
- `src/bin/competence_baseline.rs`: seeds through the CLI (`memory propose|promote|forget`, the skill written to the profile then `skill trust name@hash`), `run-mode set --ack` from the suite, tool results copied to `trials/*/tool-results/`, `--jobs N`, `axes.json` beside the bundle (or exit 1 on a refusal), and `compare --baseline <dir> --current <dir>` (exit 3 when an axis fails its gate).
- `suites/four-axis/`: 40 tasks, 10 per axis, over a new fixture `fixtures/inventory`, and `scripted-model.json`, the trajectories the tests' model server answers with (the Core never sees it). `baselines/four-axis/`: the retained baseline (bundle `e4e380fa…`, `axes.json`, `summary.md`) from a scripted-model run at 9915c074.

## Known limits
- The retained baseline is a scripted-model run: it proves the harness and the Core's capability paths end to end and gives the regression gate a reference; it is not a measurement of any model's competence. No live model has run the suite (the DR authorizes no live spend). With a deterministic model every axis is 10/10, so the 0.05 gate fails on any one regressed task; a live baseline below 100% would need its own run and the gate's floor follows it.
- The injected regression is model-side (the trajectories drop the capability calls and write stale values); no product regression is injected, since the row changes no Core behaviour.
- Event logs and tool results of the baseline run are not retained in the repository (about 5 MB); the bundle keeps each log's SHA-256 and offsets, and every test run regenerates them.
- Goals avoid the words the Core treats as a failure report (`goal_reports_failure`: "bug", "error", "fail"…): with them the Core requires a reproduction first and the scripted trajectories have none. A first draft that used them showed the Core marking such tasks ReadyForReview with no change, which the verifiers failed.
- The sub-agent axis runs under `RUN_EVERYTHING` (set by the harness as a person would); under `ASK` a merge parks on an approval, and `task run --wait` does not return while a run waits on one, so the harness's deny-by-protocol loop does not reach it (pre-existing harness behaviour). The Core's no-progress budget (3) counts `git.merge.*` calls as no progress, so the trajectories read the merged file after each commit.
- `merge` of per-task bundles does not write `axes.json`; a merged four-axis run needs its report computed separately.
- CI has not run this change; the graph stops at REAL_TESTING. Windows and Linux are untested locally.
