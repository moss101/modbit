# Task Card — PX-038 Scope policy with bounded expansion and mandatory questions

## Identity

- Task ID: PX-038
- Milestone: M3 (moved from M2 by DR-M2-002)
- Requirement: REQ-PX-038; owner: core-runtime; docs/28 §3 "Scope policy"
- Qualification: QUAL-PX-038 — the first PlanRecorded freezes the original write set; each PlanRevised carries a scope delta; Core counts out-of-plan files and revisions against the ScopePolicy bounds; beyond a bound or on an always_ask_paths match the next out-of-scope write is refused until a typed question offering continue, split or stop is answered, and a ScopeExpansionRecorded event carries the counters; in headless mode the policy default fails closed to Needs Attention; the scope metric is computed against the original plan. Negative proof: silent scope widening is rejected; a question auto-answered by the agent changes nothing; measuring scope against the last plan revision fails
- Evidence tier: real-system or production-equivalent

## Goal

Scope is bounded, not merely transparent: expansion beyond the original write set needs a decision, and the decision is recorded with the counters it was measured against.

## Existing-code audit

- classification: IMPLEMENTED in this batch (was PARTIAL: PX-016 refused a write the current plan does not declare and PlanRevised already carried its delta and reason, but nothing bounded how far a plan could be revised)
- production entry point: `crates/core-runtime/src/harness.rs` `ScopePolicy` (Alpha defaults 2 out-of-plan files, 2 revisions, an always-ask list of migrations, CI configuration, lockfiles, dependency manifests and security/policy files, `headless_resolution` FAIL_CLOSED), `HarnessState::check_write` scope gate, `scope_counters`, `scope_resolution`; `services/modbit-core/src/runtime.rs` records `ScopeExpansionRecorded`, refuses with `HARNESS_SCOPE_QUESTION_REQUIRED`, applies the user's answer on resume and ends a headless run in Needs Attention; domain `TaskEvent::ScopeExpansionRecorded`
- proof: the interactive fixture task edits a file inside the original write set, revises the plan to add a lockfile, and is refused twice for the same path (retrying without an answer changes nothing) with a `ScopeExpansionRecorded QUESTION_REQUIRED` each time and no write; the typed question offers continue, split and stop; after the user answers `continue`, `ScopeExpansionRecorded CONTINUE` carries the answer and the counters measured against the original plan (0 out-of-plan files, 1 revision), and the write lands exactly once. The headless fixture task writes two files outside the original plan (inside the bound), and the third is refused with `FAIL_CLOSED`, no write, and `TaskNeedsAttention`; `task.complete` never runs

## Note recorded with this task

A FLAG-class diff invariant whose path the current plan declares is recorded at every stage but blocks completion only until the plan states why (docs/64 §4): without that, a planned and justified lockfile edit could never complete because the completion-stage whole-diff evaluation re-raises it.

## Regression — any answer while a scope question waited decided the expansion (2026-09-25)

- Evidence tier: release-critical (permissions and policy: the scope decision gates a write; a security boundary: who may decide; recovery: the decision is rebuilt from the log after a restart).
- Found in review of the EPR-008 DI-9 unlock, which requires `Actor::User` in the same `UserQuestionAnswered` arm of `rebuild`. The PX-038 arm's own comment said "a scope question is answered by the user, never by the agent (docs/28 §3)", but the arm set `state.scope_answer` from any `UserQuestionAnswered` on the task while `scope_question_pending` was non-empty. It ignored the event's actor and which question the answer was for. Only `server.rs` `RespondToQuestion` appends that event, as `Actor::User`, and it refuses a second answer to a question, so this is defense in depth rather than a live hole. QUAL-PX-038's negative proof "a question auto-answered by the agent changes nothing" had no test: the qualification only retried the write without an answer.
- Audit: IMPLEMENTED-PARTIAL. The unlock is production-wired (the answer reaches `rebuild`, the next turn records `ScopeExpansionRecorded`, and only CONTINUE unlocks the paths), but its input is not bound to its author or its question. First missing link: the `UserQuestionAnswered` arm of `rebuild` in `services/modbit-core/src/runtime.rs`.
- Fix (`rebuild` only, no new event or field): a `UserQuestionAsked` recorded while `scope_question_pending` is non-empty marks its `question_id` as a scope question. A `UserQuestionAnswered` sets `scope_answer` only when its actor is `Actor::User(_)` and it answers one of those questions (each is consumed by its first user answer), and a scope question is still pending. The answer still becomes the result of the model's `user.ask` call as before. The legitimate path is unchanged, because the loop records `ScopeExpansionRecorded QUESTION_REQUIRED` before the model can ask, and the run suspends on the question until the user answers it.
- Proof (real Core): `px_038_only_the_users_answer_to_the_scope_question_decides_the_expansion`, a desktop task on a real repository with a scripted model.
  - Phase 0: the task asks an unrelated question, which the user answers `continue` through `RespondToQuestion` before anything waits. Its write to the always-ask `pnpm-lock.yaml` is then refused (`ScopeExpansionRecorded QUESTION_REQUIRED`) and it asks the scope question.
  - Phase A: the Core is killed, and a `UserQuestionAnswered { option_id: continue }` for the scope question is appended as `Actor::Agent("solver:<task>")` through `modbit_event_store::EventStore::append`: a well-formed event on the task's hash chain that closes the question for the loop. The restarted Core resumes under a new lease and the model reads the `continue` answer. Its retried write is refused again with `HARNESS_SCOPE_QUESTION_REQUIRED`. The log holds two `QUESTION_REQUIRED` and no CONTINUE, and no `FileChanged` for the lockfile.
  - Phase B: the user answers the next scope question `stop` through `RespondToQuestion`. The Core is killed, and a `continue` to the earlier, unrelated question is appended with the user's own actor, copied from their real answer. The restarted Core records the scope question's answer: the resolutions are `QUESTION_REQUIRED, QUESTION_REQUIRED, STOP, QUESTION_REQUIRED`, the STOP carries `paths: [pnpm-lock.yaml]` and the answer `stop`, and the next write waits again. The lockfile is never written: no `FileChanged`, and its bytes are unchanged on disk.
- Regression: `qual_px_038_scope_expansion_is_bounded_asks_a_typed_question_and_fails_closed_headless` (the user's `continue` still records CONTINUE, and the write lands once), `qual_px_016_…`, and the other surface tests that answer typed questions (`qual_ev_0222_px_014_…`, `qual_ev_0077_0122_…`, `qual_ev_0118_…`, `qual_ev_0151_0275_…`, `qual_ev_0096_…`, `qual_ev_0174_…`, `qual_px_040_…`) pass. See `local-green-targeted.log`.
- Fault injection: the test was written and run before the fix, in two stages.
  - On the unfixed Core, phase A fails: after the agent's `continue`, the retried `change.apply` returned `status: SUCCESS` and wrote `pnpm-lock.yaml` (`local-red-unfixed.log`).
  - With the actor check alone, phase A passes and phase B fails: the resolutions are `QUESTION_REQUIRED, QUESTION_REQUIRED, CONTINUE`. The user's later `continue` to the earlier question overrode their `stop` to the scope question, and the lockfile was written (`local-red-actor-check-only.log`).
  - Only the full fix passes.
- Limitation, a follow-up and not part of this regression: `ScopeExpansionRecorded` is recorded under the run's agent actor (`solver:<task>`, `run_loop`), and `rebuild` applies a CONTINUE whatever its actor. So an event forged directly as `ScopeExpansionRecorded CONTINUE` would still unlock the path. Closing that means recording the decision as the Core, as DI-9's `ProtectedPathsUnlocked` is (`Actor::Core`), and honouring only Core-recorded decisions. That changes the event's recorded actor.

## Regression — a recorded scope answer decided a later expansion (2026-09-26)

- Evidence tier: release-critical (permissions and policy: the scope decision gates a write; recovery: the decision is rebuilt from the log after a restart).
- Found in the audit for the limitation above (the next regression below), and fixed in the session that owned this regression. That session prepared the fix as a local commit and ended before this card section, the reseal and the push; the commit was carried to the remote on the regression-2 branch with its logs unchanged.
- Defect: `rebuild` kept `scope_answer` after replaying the `ScopeExpansionRecorded` decision made from it, because only the loop's own turn took the answer. After any resume that followed a recorded answer (for example the user answering an unrelated question), the first new scope refusal in that run made a path wait, and the next turn's loop top recorded a decision for it from the old answer. No question was asked and no forged event was needed.
- Audit: IMPLEMENTED-PARTIAL; first missing link, the `ScopeExpansionRecorded` arm of `rebuild` in `services/modbit-core/src/runtime.rs`.
- Fix (`rebuild` only): a replayed decision consumes the answer it was made from, so `CONTINUE`, and `STOP`, `SPLIT` or `FAIL_CLOSED`, clear `scope_answer`, and a later expansion waits for its own answer.
- Proof (real Core, no forged event): `px_038_a_recorded_scope_answer_decides_only_its_own_expansion`. A desktop task's write to `pnpm-lock.yaml` waits; the user answers the scope question `continue` and the write lands. The task then asks an unrelated question, which the user answers `no`. In the resumed run its write to `yarn.lock` is refused on every retry, the model is left to ask its own question, and `yarn.lock` is never written. The shared helpers `px_038_run`, `px_038_open_question` and `px_038_answer` moved to module level for the PX-038 tests.
- Fault injection: before the fix the test fails. The resumed run recorded `CONTINUE` for `yarn.lock` from the earlier `continue` for `pnpm-lock.yaml`, with no question asked (`local-red-stale-answer.log`). With the fix it passes, with the targeted set of the first regression (`local-green-targeted-2.log`).
## Regression — a scope decision the Core did not record opened a path (2026-09-26)

- Evidence tier: release-critical. The change alters the recorded actor of an event (evidence semantics), which decision `rebuild` honours after a restart (recovery), and who may open a write beyond the scope bounds (permissions, a security boundary).
- Found as the limitation recorded by the first regression above (the stale answer, above, was found in the same audit). `ScopeExpansionRecorded` was appended under the run's agent actor (`Actor::Agent("solver:<task>")`) by both writers in `run_loop`: the refusal that asks (`QUESTION_REQUIRED`, or `FAIL_CLOSED` headless) and the loop-top record of the user's answer (`CONTINUE` / `SPLIT` / `STOP`). The `ScopeExpansionRecorded` arm of `rebuild` applied a `CONTINUE` whatever its actor, and whether or not anyone had answered. A `CONTINUE` written straight into the log (for example through `EventStore::append` while the Core is down) therefore opened an out-of-scope write after a restart, even before any scope question existed, or after the user answered `stop`.
- Audit: IMPLEMENTED-PARTIAL; first missing link, the `CONTINUE` branch of the `ScopeExpansionRecorded` arm of `rebuild` in `services/modbit-core/src/runtime.rs`. Every writer and reader of the event was traced:
  - writers: only `run_loop`'s two appends. Nothing else in the workspace, the protocol, the CLI or the desktop appends it.
  - readers: only `rebuild`. Accounting (`accounting.rs`) keys actors only for the user's interventions of other event types; `baseline.rs`, `attention.rs` and `branch.rs` read the question events, not this one, and a fork carries answers, not scope records; the doc 63 scope metrics (`benchmarks/agent-engineering`) count `PlanRevised` and `UserQuestionAsked`; no client renders an event's actor. None depends on who recorded the decision.
  - schema: docs/30 lists `ScopeExpansionRecorded` under Competence with no actor, docs/13 and docs/31 define the actor generically, and the payload and `schema_version` are unchanged. No locked row, disposition, owner or locked file changes, so no Decision Record is required (docs/02, `tools/architecture-lint/rules.toml`).
- Fix (`runtime.rs` only, no new event or field):
  - Both writers record as `Actor::Core("scope-policy")`: the decision is the Core's scope policy, and the agent's own action stays on its tool-call events. The loop opens the paths only once its `CONTINUE` is on the log ("nothing on the log, nothing open", as DI-9's `ProtectedPathsUnlocked`).
  - `rebuild` opens paths on a `CONTINUE` the Core recorded, as recorded, so replaying an old Core decision never depends on today's derivation.
  - Old logs: every `CONTINUE` recorded before this change carries the agent actor. A `CONTINUE` under any actor other than the Core is honoured only when it stands for the user's own `continue` to the scope question, already rebuilt (`scope_answer`, which since the first regression is set only by `Actor::User` answering a question asked while the expansion waited), and names exactly the waiting paths; it then consumes that answer. Any other such `CONTINUE` changes nothing: no path opens, and the waiting paths and the user's answer stay, so the Core records the user's decision itself at the next turn. Records that open nothing (`QUESTION_REQUIRED`, `STOP`, `SPLIT`, `FAIL_CLOSED`) apply whoever wrote them, so an old log's waits and refusals rebuild as before.
  - `QUESTION_REQUIRED` in `rebuild` now adds its paths to those waiting, as the live loop does, instead of replacing them. Before, a task refused on two paths before one question rebuilt waiting on the last path only, so after a restart the user's `continue` opened one of the two, and an old record naming both could not match.
- Proof (real Core): `px_038_only_a_scope_decision_the_core_recorded_opens_a_path`, a desktop task on a real repository with a scripted model; each forgery is appended through `modbit_event_store::EventStore::append` with the Core killed, and each phase is checked by reading the log back with its actors.
  - Phase 1: the task asks an unrelated question, which the user answers. A `CONTINUE` for `pnpm-lock.yaml` is appended as the agent before any scope question exists. The restarted Core refuses the lockfile write and records `QUESTION_REQUIRED` as the Core; nothing is written.
  - Phase 2: the user answers scope question (1) `stop`, and an agent `CONTINUE` for the lockfile is appended after that answer. The restarted Core records `STOP` as the Core, and the retried write is refused again with a new `QUESTION_REQUIRED`.
  - Phase 3 (fault injection): the user answers scope question (2) `continue`. A Core started with `MODBIT_FAULT_KILL_BEFORE_EVENT=ScopeExpansionRecorded:1` aborts right before committing its `CONTINUE`; the log holds no decision and no write. The next Core rebuilds the answer, records `CONTINUE` once, as the Core, and the lockfile is written once.
  - Phase 4 (old logs): the writes of `yarn.lock` and `poetry.lock` are both refused before scope question (3), which the user answers `continue`. A `CONTINUE` naming both is appended exactly as a Core before this change wrote it (agent actor, reason `answered`, answer `continue `). The restarted Core honours it as the record of the user's answer: both files are written once, and the Core records no second decision.
- Fault injection, the test run before the fix, in stages (`local-red-2-*.log`, excerpts; the assertion's dump of the task log is elided):
  - #43's code as it stood (b517c21): phase 1 fails. The agent's `CONTINUE` opened the lockfile before any question, no `QUESTION_REQUIRED` was recorded, and the lockfile was written (`local-red-2-unfixed.log`).
  - Core writers and a Core-only `CONTINUE`, nothing else: phases 1–3 pass, and phase 4 fails. The old record is ignored, rebuild waits on `poetry.lock` only, the Core records a second `CONTINUE` for it, and `yarn.lock` is refused again (`local-red-2-actor-gate-only.log`).
  - Plus the rule for old records, with `QUESTION_REQUIRED` still replacing the waiting paths: phase 4 still fails the same way, because the old record naming both paths does not match (`local-red-2-no-accumulation.log`).
  - Only the full fix passes.
- Regression: the earlier regressions' `px_038_only_the_users_answer_to_the_scope_question_decides_the_expansion` and `px_038_a_recorded_scope_answer_decides_only_its_own_expansion`, `qual_px_038_…`, `qual_px_016_…`, the surface tests that answer typed questions (`qual_ev_0222_px_014_…`, `qual_ev_0077_0122_…`, `qual_ev_0118_…`, `qual_ev_0151_0275_…`, `qual_ev_0096_…`, `qual_ev_0174_…`, `qual_px_040_…`), the M4.6 kill-point suite and the M4.2 compaction proofs pass on top of both earlier fixes; `cargo fmt --check`, `cargo clippy -p modbit-core --all-targets` and the Core's unit tests are clean (`local-green-2-targeted.log`).
- Residual, stated not closed: the boundary is the recorded actor, as for DI-9's `ProtectedPathsUnlocked`. A record appended under the Core's own actor by whoever holds the store is outside it; that is the log's tamper evidence, not the scope policy. A `QUESTION_REQUIRED` written by another actor only makes a path wait: the path still needs the user's answer, and `check_write` still requires the plan to declare it, which the agent can already bring about by revising the plan and attempting the write. A `STOP` written by another actor can only drop a pending answer; the retried write is refused and asks again.
