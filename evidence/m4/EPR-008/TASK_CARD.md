## Regression — DI-9 matched the policy's patterns with a second, prefix-only matcher (2026-09-24)

- Evidence tier: release-critical (permissions/policy and a security boundary: the change engine's write gate).
- Found in review of this task's DI-9 wiring. `run_loop` sets `state.protected_paths` from the policy's `question_required_patterns()` and `invariant_context` hands them to `modbit_verification::evaluate_file` / `evaluate_diff`, but `crates/verification/src/invariants.rs` matched them with `path.starts_with(pattern)`, while the patterns are written in `ProtectedSurface::matches` grammar (directory prefix `.github/`, segment `/deploy/`, suffix `.tf`, basename `Dockerfile`). Of the four question-required surfaces (CI/CD, infrastructure, deploy, policy), no segment pattern (`/terraform/`, `/infra/`, `/k8s/`, `/helm/`, `/deploy/`, `/deployment/`, `/release/`) matched a relative path, `.tf` matched no Terraform file, and `Dockerfile`, `docker-compose.yml` and `Jenkinsfile` matched only at the repository root. So a write to `deploy/prod.yaml` or `infra/main.tf` never raised DI-9 and landed without a typed question.
- Audit: BROKEN-DRIFTED. The wiring read the right source but matched it with a second matcher. First missing link: the DI-9 predicate in `evaluate_file`.
- Fix: one matcher. `ProtectedSurface::matches` now delegates to the associated `ProtectedSurface::matches_patterns(patterns, path)`, which keeps the grammar unchanged and is owned by `crates/policy`. DI-9 calls it with the context's patterns. `modbit-verification` already depended on `modbit-policy`, so the fix adds no dependency edge and no cycle (`tools/architecture-lint/rules.toml`). The Core's fallback when no policy is resolved (`.github/`, `.modbit/`) decides every tested path exactly as the old prefix match did. The risk rules are untouched, so `REALIZED_RISK_RULES_VERSION` and the default policy version do not move.
- Proof (unit tests in `crates/verification`):
  - `di_9_denies_a_protected_segment_anywhere_in_the_path`
  - `di_9_denies_a_protected_suffix_at_any_depth`
  - `di_9_denies_a_protected_basename_in_any_directory`
  - `di_9_denies_a_root_directory_prefix_and_the_fallback_defaults_behave_as_before`
  - `di_9_and_the_risk_rules_agree_on_every_path`, which pins DI-9 to `AssurancePolicy::surfaces_of(..)` with `question_required` over the whole path corpus.
- Proof (real Core): `epr_008_di_9_refuses_a_nested_deploy_write_without_a_typed_question`. A plan declares `services/api/deploy/prod.yaml`, `infra/main.tf` and `src/notes.txt`, and no typed question is asked. Both protected writes are refused before any effect: `DiffInvariantViolated` DI-9 DENY at TRANSACTION, `StepFailed` `DIFF_INVARIANT_DENY`, the model is told the reason, and neither file reaches the disk. The plain write lands, it is the only `change.apply` that reaches the effector, and the task reaches `ReadyForReview`.
- Fault injection: the new tests were written and run before the fix. On the prefix matcher, four of the five unit tests fail (on `deploy/prod.yaml`, `infra/main.tf` and `services/api/Dockerfile`), and the Core test fails because the log holds no `DiffInvariantViolated` at all for `services/api/deploy/prod.yaml`. The root-prefix and fallback test passes both before and after, as it must.
- Limitation: DI-9 is a permanent DENY. No answered typed question lifts it, because `UserQuestionAnswered` feeds only the scope-expansion unlock of docs/28 §3, so a task cannot change a protected path even after the user agrees. This fix extends that existing behaviour from root-level paths to every path the policy protects. The unlock was a follow-up and was not part of this regression; the next regression below (2026-09-25) adds it.

## Regression — DI-9 was a permanent DENY: no answered typed question lifted it (2026-09-25)

- Evidence tier: release-critical. The change touches permissions and policy, a security boundary (the change engine's write gate) and the event schema (a new `ProtectedPathsUnlocked` task event and a `protected_paths` field on `UserQuestionAsked`).
- Found: the regression above extended an existing gap to every protected path. docs/64 §4 says a protected path changes "only after a typed question", but in production:
  - `evaluate_file` raised DI-9 whenever the path matched `ctx.protected_paths`;
  - `invariant_context` filled those paths from the policy without reference to any answered question;
  - `UserQuestionAnswered` fed only the scope-expansion unlock of docs/28 §3.
  So after the model asked to change `deploy/prod.yaml` and the user said yes, the write was still refused `DIFF_INVARIANT_DENY`, and a task could never change a protected path.
- Audit: IMPLEMENTED-PARTIAL. The DENY half was wired; the typed-question half did not exist. First missing link: nothing carried an answered question into `InvariantContext`.
- Owner: EPR-008, for three reasons: DI-9's paths are this task's `question_required` surfaces, the card above names the unlock as this task's follow-up, and docs/23's EPR-008 as-built paragraph states the rule. PX-037 (DI-1..DI-9 evaluation) and PX-038 (scope questions) keep their behaviour. No second matcher, question service or event store was added.
- Design:
  - **Which question counts.** A `user.ask` that names the paths in its new `paths` argument. `handle_ask` keeps the named paths that DI-9 protects under the task's policy (the policy's `ProtectedSurface::matches_patterns` on paths normalized by `modbit_verification::protected_path_key`) and records them on `UserQuestionAsked.protected_paths`. It then sets the options itself, whatever the model wrote: `continue` and `stop`, each labelled with the paths, with free text off. The user answers exactly what the Core will do.
  - **Which answer counts.** Only a `UserQuestionAnswered` choosing `continue` on that question and appended by `Actor::User`, which is what the SurfaceProtocol's `RespondToQuestion` writes. None of these unlocks anything: an answer on the log from any other actor, a `stop`, a question that names no path, or one that names another path.
  - **On the log.** The resumed run's next turn appends `ProtectedPathsUnlocked {question_id, paths, answer}` as `Actor::Core("change-engine")`. `rebuild` reads it back (only from the Core) into `HarnessState.protected_unlocked`, so a restarted Core rebuilds the unlock and never records it twice.
  - **In the change engine.** `InvariantContext.protected_unlocked` holds exact paths, never patterns. `evaluate_file` skips DI-9 for exactly those paths and still matches everything else with the policy's own matcher. The per-transaction and the COMPLETION evaluation use the same context.
  - **Fail closed.** `protected_question_unavailable` covers a profile in `no_approval_profiles` (unattended) and a headless task (origin neither desktop nor IDE, the scope rule's definition, now shared as `headless()`). There the `user.ask` naming a protected path is refused `PROTECTED_PATH_FAIL_CLOSED`: the run does not suspend and no question is recorded. The DI-9 refusal tells the model that the path stays closed and why. A protected path is never auto-allowed, whatever `ScopePolicy.headless_resolution` says. In an attended task, the refusal tells the model how the path opens.
- Proof (real Core, `services/modbit-core/tests/surface_protocol.rs`):

The model asks with `paths` and yes/no options; the user sees the Core's `continue`/`stop` labelled with the path, and the run suspends. The user answers `continue` through `RespondToQuestion`, and the resumed run records one `ProtectedPathsUnlocked`. The Core is killed while the task waits on an unrelated question (whose options stay the model's). The restarted Core rebuilds the unlock: the same write lands once after it, the COMPLETION run raises no DI-9, no second unlock is recorded, the task reaches `ReadyForReview` and the disk holds the new content.
  - `epr_008_di_9_a_question_that_does_not_name_the_path_or_is_declined_unlocks_nothing`: three questions leave `deploy/prod.yaml` closed. The user says yes to a question naming no path, continues on a question naming `deploy/staging.yaml`, and stops on the question naming this path.   - Unit (`crates/verification`): `di_9_opens_exactly_the_paths_the_user_unlocked`. An unlocked path opens with `./` and `\` normalization; siblings, a nested path of the same name, a `.bak` and every file under an "unlocked" directory stay closed; nothing opens without an unlock.
