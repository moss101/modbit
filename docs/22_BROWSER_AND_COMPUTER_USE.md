## Locked direction

Modbit does **not** build a new browser engine and does not operate primarily from screenshots. It builds an agent-native semantic runtime over Chromium while exposing the exact same live session to the user.

## Local browser

Electron main creates a sandboxed `WebContentsView` in a dedicated session partition with Node disabled and strict context isolation. A Browser Bridge controls that same `webContents` through Chrome DevTools Protocol. The renderer only hosts/choreographs the view; untrusted page content never gets Modbit privileged APIs.

As built (M7.1): `apps/desktop/src/main/browser.ts` (`BrowserHost`) creates one `WebContentsView` per browser session in the session's own persisted partition (`persist:modbit-browser-<id>`) with `sandbox`, `contextIsolation`, no `nodeIntegration` (also none in workers or subframes), no preload, no `webviewTag`; the view opens no windows, downloads nothing, is granted no permission or device, and is never navigated anywhere but http(s) (`will-navigate` / `will-redirect` blocked). The host attaches the view to the Core's session over the desktop's authenticated surface connection (`AttachBrowserHost`, a `browser.host` client capability only the desktop kind holds — REQ-EV-0110 — stating the view's isolation; the Core refuses a view without it, `HOST_NOT_ISOLATED`, and a partition other than the session's) and answers the Core's `BrowserHostRequest` frames on that connection (`BrowserHostResponse`) through `webContents.debugger` (CDP 1.3): `navigate` (`loadURL`, the settled page state), `state`, `snapshot` (`Accessibility.getFullAXTree`, bounded, unignored nodes with role, name, value and depth), `capture` (`webContents.capturePage` with a clip, normalized to CSS pixels; a view hidden with the panel is parked back in the window for the capture — beside it, out of sight, or in place for the instant it takes — because off the window Chromium composites no frame on Linux and Windows and neither CDP's screenshot nor `capturePage` ever answers there; a slow capture is `CAPTURE_TIMEOUT`, never an unanswered request), `isolation` (asked of the page: `process`, `require`, `window.electron` all absent), `close`. `crates/browser` is the protocol (`BrowserSessionId`, `ControlLease` with `Controller` and a fencing generation, `HostRequest` / `HostResponse`, `PageState` with its fingerprint, `AxNode`, `BrowserPort`, `navigable`); `services/modbit-core/src/browser.rs` owns the sessions (open per task, journaled `BrowserSessionOpened` / `BrowserHostAttached` / `BrowserNavigated` / `BrowserSessionClosed`, rebuilt from the task's events after a restart so a host attaches again to the same partition; a host that disconnects fails every request it owed `HOST_GONE`; a request under the user's control lease is refused `HUMAN_ACTIVE` before it reaches the host); `crates/tools/src/browser.rs` is the family (`browser.navigate`, `browser.snapshot`: ReadOnly, `browser.control` in the trusted and autonomous leases, `NAVIGATION_BLOCKED` for anything but http(s) before anything is sent, every page-derived string tagged `UNTRUSTED_WEB_CONTENT`; a navigation is progress, reading the page again is not). The renderer's Browser panel places the view over its placeholder and shows only what the host and the Core report (URL, title, state version, the lease, the isolation probe) — page content never enters the window. Proven on the real Core with a fake host over the real protocol (`qual_m7_1_…`) and in the real app against a real page (`apps/desktop/e2e/browser.spec.ts`): the agent's navigation and snapshot reach the model tagged untrusted with the page's instruction-shaped title left as data; the view the person opens is the one the agent drove. Semantic entities and stable references (M7.2), deltas (M7.3), semantic actions (M7.4), the visual fallback (M7.5), the takeover (M7.6; the lease and its fencing exist) follow. IMP-EV-0081 (docs/32 "Security settings"): the view is a worker on the same canonical contracts — its process dying (`render-process-gone`) is the host's to mend, not the Core's: the host restarts the view at the page it was on, re-establishes the CDP bridge and attaches again to the same session (the same id, partition, lease generation and controller; `BrowserHostAttached` journaled again), answering `VIEW_RESTARTING` to a request that arrives meanwhile; the Core, its log and the task are untouched, and the agent's next observation reads the restarted page (`apps/desktop/e2e/workers.spec.ts`).

## Cloud browser

Chromium runs inside the isolated MicroVM. Browser Bridge connects through authenticated remote CDP; user view is streamed through remote display/WebRTC/VNC-style transport. Structural and visual control share one BrowserSessionId.

As built (M8.8): a `cloud_isolated` task's browser is a headless Chromium inside its sandbox — Chrome for Testing's headless shell in the MicroVM image (`tools/guest-image/build.sh` with the shell's tree, its shared-library closure, NSS's modules and a font), the host's Chrome under the reference backend — started by the guest on the sandbox's policy (`browser.start`, `GuestPolicy.browser`, granted when the task's lease carries `browser.control`; `SandboxLeaseAcquired.browser`), its DevTools bound to the guest's loopback and reachable by one path only: an admitted guest link the gateway turns into a byte relay (`browser.forward`) behind `GET /v1/sandboxes/{id}/browser/cdp` (WebSocket, worker bearer token). The browser has no network of its own: it is pointed at the guest's egress proxy with the loopback bypass removed, so every request — a page on the admitted host, Chromium's own background traffic — is the broker's decision and on the audit. The Browser Bridge is the Core itself (`services/modbit-core/src/browser_cloud.rs`, host kind `cloud-cdp`): when a cloud task starts with a browser in its sandbox the Core opens the task's browser session and attaches an in-process host that speaks CDP over the relay (`Target.createBrowserContext` — an ephemeral context, in-memory cookies and storage — one page target, flattened session), answering the same requests the desktop's Electron host answers: `navigate` (`Page.navigate`, settled at the load), `state`, `snapshot` (`Accessibility.getFullAXTree`, `DOM.getBoxModel` for the actionable nodes), `capture` (`Page.captureScreenshot` with a clip), `act` (`DOM.resolveNode`, a real click at the element's box after a hit test, `Input.insertText` after a focus, `Input.dispatchKeyEvent`, a settle at the navigation it started or a quiet period; a dialog reported `MODAL_BLOCKING`), `isolation`, `close`; the compiler, the ladder, the control lease and the log events are the local browser's. `fill_credential` is refused `CREDENTIAL_UNAVAILABLE` in the cloud: page credentials are the desktop broker's custody. The person's view is the page's screencast (`Page.startScreencast`, JPEG), served to every surface connection that watches the session (`WatchBrowserView` → `SurfaceFrame.browser_frame`, `BrowserViewFrame {jpeg, page_width, page_height, seq, url, title}`; `UnwatchBrowserView`; the screencast runs only while someone watches), and the person's input goes in as `BrowserViewInput` (mouse, wheel, keys, text, in page CSS pixels) — applied by the same host through CDP, only while the person holds the session's control lease (`SetBrowserControl USER`), refused `AGENT_ACTIVE` otherwise; taking control blocks the agent's input as it does locally (M7.6). Remote to the person: the worker keeps one outbound link to the Cloud API (`GET /v1/workers/link`, its worker token; no inbound port on a worker — docs/24), over which the API asks the worker to watch, to apply input or to hand control, and the worker sends the frames; the person's client streams `GET /v1/browser-sessions/{id}/stream?session_id=` (WSS: a `watching` opener, then `frame` messages) and posts `POST /v1/browser-sessions/{id}:input` and `:control`, each answered with the worker's Core's outcome. Proven by the conformance steps `browser_started`, `browser_answers_cdp`, `browser_stopped` on the MicroVM and the reference backend, and end to end by the cloud worker (`qual_m8_8_…`: the agent's `browser.navigate`, `browser.snapshot`, `browser.act fill`, `browser.act click` with a postcondition, on a page reached through the broker; `AGENT_ACTIVE` for input under the agent; `USER` control; a JPEG frame of the greeting page over the API's stream; the person's click in the view navigating the page; control back; the agent reading the page the person left; `BrowserControlChanged` on the log both ways). Not built: the desktop's rendering of the API stream (the transport is proven with a protocol client), WebRTC (frames are JPEG over WebSocket), a per-tenant choice of browser image.

## Semantic Browser Compiler

```text
Chromium/CDP
  ├─ Accessibility tree
  ├─ DOM/layout metadata
  ├─ URL/navigation/network state
  ├─ form/control state
  └─ targeted screenshot regions
          ↓
Semantic Compiler
  ├─ persistent semantic entity IDs
  ├─ page classification
  ├─ action derivation
  ├─ intent filtering
  ├─ state fingerprint
  ├─ delta/diff generation
  └─ page transition graph
          ↓
Agent-facing actions
```

Inspired mechanisms include accessibility snapshots/stable refs, page diffs, semantic action grouping, state graphs and targeted visual fallback. Full AX snapshots are not repeatedly dumped into context; after initial state, incremental semantic patches are preferred.

As built (M7.2, the first stage): `crates/browser/src/compiler.rs` fuses the host's raw tree — each accessible node with the DOM node behind it (`backendDOMNodeId`), its landmark ancestry and, for actionable nodes, the layout box the host fetched (`DOM.getBoxModel`, bounded) — into a compact `PageEntities`: actions (buttons, links, menu items, tabs…), fields (text boxes, combo boxes, check boxes, radios…) and landmarks (main, navigation, form, dialog, headings…), each with a **stable reference** (12 hex of sha256 over role, accessible name, landmark path and ordinal among look-alikes — never a DOM node id, which is per state version and never leaves the Core), plus the page's visible text (headings, paragraphs; bounded) as data, and an entity hash that is the same for two versions with the same identities. `browser.snapshot` returns the compiled page; `browser.inspect {ref}` compiles the page again and resolves the reference by identity: the same element at its new version (new node id, current value and box), or `TARGET_STALE` naming the look-alikes that remain (same role and name, by reference) — never the node that now sits where the element was (REQ-EV-0278). `BrowserPort::remember_page` / `known_entity` keep what every compiled page named, so a stale reference is explained even after several re-renders. Proven with a fake host that re-renders the page with fresh node ids and renames the form's button (`qual_m7_2_…`), and in the real app on a real page re-served with the button renamed (`browser.spec.ts`): the field's reference resolves again with its box, the button's reference is stale with the outer look-alike named. Deltas (M7.3), actions on references with postconditions (M7.4) and the page transition graph follow.

As built (M7.3): `compiler::state_fingerprint` is the content fingerprint of a compiled page (URL, title, entity identities, the fields' values and disabled state) — what a postcondition compares and what a delta goes between; a mutation the host's version counter did not see still moves it. `compiler::diff` is the bounded semantic delta between two compiled pages (entities added, removed and changed with before/after values; text lines added and removed; a new URL or title) and `compiler::apply` its equivalence (the delta applied to the previous state is the next). After the first read of a session `browser.snapshot` answers with the delta since the last read (`mode: delta`, `from_version`, `from_fingerprint` → `state_fingerprint`, `unchanged`), unless the caller asks for `mode: full` or the change is most of the page — then the full page comes back with `delta_fallback` (the rehydrate fallback). Every read is on the task's log as `BrowserPageObserved` (version, fingerprints, entity hash, mode, counts, URL): the delta stream. Proven with a forty-message inbox (`qual_m7_3_…`): an unchanged read costs under a fifth of the page, a one-message delta under a quarter, a different screen rehydrates in full with a new fingerprint, `full` is honoured; and on the real page (`browser.spec.ts`): the read after a navigation names the renamed button and nothing else. What the host's version counter sees is navigation and load; DOM mutations between reads are found by the fingerprint at the next read (a mutation observer over CDP is M7.4's postcondition substrate).

## Action hierarchy

1. Native website-declared or browser-native structured action when trusted and policy-allowed.
2. Derived semantic action (`fill login.email`, `click checkout.submit`).
3. Primitive structural CDP action.
4. Targeted screenshot/vision action for canvas/unlabeled/visual-only region.
5. Full screenshot only as last-resort diagnostic evidence.

As built (IMP-EV-0082/0088/0089/0090, on M7.2–M7.5): the ladder in force is semantic state → structural CDP action → targeted region capture and point click; the accessible form completes with the host never asked for a pixel, the drawn control escalates explicitly (`qual_ev_0082_0234_0277_0282_…`). Risk is target × action × data × context (`classify_action`): a submission, a consequential name, a form button, an unlabeled visual region and — by its data — a credential fill (`fill_credential`) are protected and wait for the person's approval of the exact intent; a target the compiler never named is judged page-only and refused `ACTION_UNSAFE` when it turns out protected. Failures are the typed taxonomy with recovery guidance on every one (`FAILURE_TAXONOMY` in `crates/tools/src/browser.rs`): `TARGET_STALE`, `TARGET_OCCLUDED` (the host hit-tests the click point: what is there must be the element or inside it), `WINDOW_UNVERIFIABLE` (the answering view must be the exact web contents attached — IMP-EV-0083; the host also reports the web contents id and OS process id, and a page's title is never an identity), `ACCESSIBILITY_UNAVAILABLE` (a loaded page with no tree), `HUMAN_ACTIVE`, `MODAL_BLOCKING` (a JavaScript dialog holds the page; reads and actions both wait for the person), `TARGET_NOT_EDITABLE` (the destination is verified a writable text entry before anything is replaced; text enters as typed input and never through the clipboard — IMP-EV-0090), `ACTION_UNSAFE`, `PERMISSION_REQUIRED` (the session grants no permission; the one the page asked for is named on the action), `STALE_GENERATION`, `NAVIGATION_BLOCKED`, `EMERGENCY_STOPPED`. Proven per code on the real Core (`qual_ev_0089_…`) and on a real page (`browser.spec.ts` faults test: an overlay, a div, a geolocation request, an alert; the clipboard secret intact).

As built (M7.4): `browser.act {ref, action, value?, key?, expect?}` acts on an entity by reference — `click`, `fill`, `select`, `check` / `uncheck`, `press` — resolving it by identity at the current page first (`TARGET_STALE` does nothing; `TARGET_DISABLED`), then asking the host to act on the DOM node behind it as a person would (`apps/desktop/src/main/browser.ts`: `DOM.resolveNode`, a real click at the element's box through `Input.dispatchMouseEvent`, focus and `Input.insertText` for a fill, real key events for a press, `select` by option text or value; then a settle: the navigation the action started, or a short quiet period), and reading the page again: the answer is the state after, the delta since before, the fingerprints and whether the declared postcondition held (`expect`: `url_contains`, `text_contains`, `changed`, `value {ref, equals}`; a miss is `POSTCONDITION_FAILED` with the action recorded as done). The effect is per call (docs/17 "Yes by effect"): `Tool::effect_of` classifies the resolved entity (`compiler::classify_action`, the first cut of the semantic UI risk classification) — filling a field, toggling, a tab or an in-page link is a `ReversibleWrite` of the page; a submission or a consequential action (a form's button, Enter in a form, pay / buy / send / delete / sign in / agree / …) is an `ExternalSideEffect` the kernel binds to an approval by intent and receipts; the pipeline judges the class the tool returns, never below the registered one, and `act` refuses at run time an element it finds protected under a page-only judgement (`ACTION_UNSAFE`: read the page and act again). Every performed action is on the log as `BrowserActionPerformed` — identity, effect class, the fingerprints before and after, whether it navigated, the postcondition's verdict (REQ-EV-0280's transition evidence). Proven on the real Core with a fake host (`qual_m7_4_…`: the fill runs at once with its value postcondition, a dead link fails its postcondition with the click recorded, a stale reference does nothing, the submission opens an approval before anything reaches the host and runs once after it, three transitions on the log) and in the real app on a real form (`browser.spec.ts`: the fields filled on the live page, the submission approved on the task card, the form's GET landing on the welcome page with the postcondition held, the view showing the welcome page).

As built (M9.4, IMP-EV-0281, DR-M7-001): rung 1 is a structured action **the site offers and the host trusts**. The host binds an external tool server to the origins it serves (`sites` in its configuration, `crates/mcp::ServerConfig`); a page at one of those origins has a structured way to do what the agent would otherwise do by driving its interface. Every page read carries `site_tools` — the bound server's tools by qualified name when this task can reach it (trusted, leased, answering), and, when it cannot, which server and why (`EXTERNAL_SERVER_UNTRUSTED`, `EXTERNAL_CAPABILITY_NOT_LEASED`, a transport failure) — so the fallback down the ladder is stated rather than silent. A **protected** action (a submission or a consequential action) is then refused `SITE_TOOL_PREFERRED` naming the tool to call instead; a page-only action still goes through the interface, and so does everything at an origin with no reachable server, which is the M7.4 rung this falls back to. Ordering: the Capability Kernel judges the class before any effector runs and sees only the class, never the page, so an approval for the click is asked before the refusal can be given — a model that read the page never gets there. Binding is the host's declaration, not the page's: a page is untrusted content (docs/23), so what a page says about its own tools can only ever be a **proposal** (`ProposeExternalServer`, REQ-EV-0224), never a grant. Proof: `qual_ev_0281_a_site_tool_is_preferred_for_a_protected_action_when_trust_allows_and_the_page_is_the_fallback` — one cart page and one "Place order" button, driven through the interface while the server is untrusted and refused in favour of `external.shop.order` once a person trusts it.

As built (M7.5): the compiler marks **visual regions** — a canvas always, an image or figure without an accessible name, a graphics document — with a stable reference, the reason the semantic state is insufficient and the layout box (`PageEntities.visual_regions`; the host fetches boxes for those roles too); they are never entities. `browser.capture {ref, reason?}` captures **that region only** (`webContents.capturePage` with the clip, normalized to CSS pixels; an entity's box is capturable too) and hands the bytes to the media pipeline like any image read (docs/25: metadata stripped, provenance `browser:<url>#<ref>`, budget, untrusted) — the model receives the region as an image part, never the page; the answer carries the compiler's reason and the model's stated one. `browser.act {ref, action: click, at: {x, y}}` clicks a point inside the region's box (the host clamps it to the box; a canvas is page-only, an unlabeled image is protected until a person says otherwise), and the read after verifies the postcondition like any action. Both are on the log: `BrowserRegionCaptured` (region, role, reason, box, egress reference, fingerprint) and `BrowserActionPerformed.visual_fallback` (the point and the reason). Proven on the real Core with a fake host (`qual_m7_5_…`: the region marked, the clip requested is exactly the canvas's box, the image reaches the model as an image part, the point click's postcondition holds, both records on the log) and in the real app on a real `<canvas>` colour picker (`browser.spec.ts`: a 240×60 PNG of the canvas, a click at three quarters of its width, `picked: green` in the page's `<output>`).

## Live user takeover

Browser session has a control lease. User takeover immediately blocks agent input, not observation. Returning control increments lease generation to fence stale input events. The session does not restart.

As built (M7.6): the control lease lives in `crates/browser::ControlLease` (`Controller::Agent | User`, a generation that increments on every hand-over; `admits_agent_input(generation)`). `SetBrowserControl {browser_session_id, controller, task_id}` (a `session.control` command under the session lease) moves it on the Core — journaled as `BrowserControlChanged`, rebuilt after a restart, a hand-over to the holder a no-op — and the desktop's Browser panel offers "Take control" / "Return control to the agent" (`browser:control`), showing who holds it and the generation (`takeover active` as the panel's state). Agent input is blocked in two places and observation in neither: the Core refuses `browser.navigate` / `browser.act` under the person's control before anything reaches the host (`HUMAN_ACTIVE`), while `browser.snapshot` / `browser.inspect` / `browser.capture` still run; the host (`apps/desktop/src/main/lease.ts`, `admitsAgentInput`) learns each new generation before the hand-over is acknowledged and fences any agent input stamped with an older one (`STALE_GENERATION`) — an input from before a takeover never lands after it, even once the agent holds control again. The session never restarts: the person types into the same view (`typeAsPerson` sends the person's key events for the E2E) and the agent reads what they typed. Proven on the real Core (`qual_m7_6_…`: the refused navigation never reaches the host, the read does, generations 1 → 2 → 3 on the requests, two `BrowserControlChanged` on the log, the lease rebuilt after a restart), on the host's rule (`lease.test.ts`) and in the real app (`browser.spec.ts` takeover test: the person takes control while the agent's run is live, types into the login form, the agent's fill is refused and its read shows the person's text, control returns at generation 3 and the agent's fill lands with its postcondition).

As built (IMP-EV-0084/0085/0087/0110, on M7.6): one controller per session — the lease is the agent's or the person's, and one host per session: a second host connection is refused `HOST_CONFLICT` until the holder's connection is gone (`qual_ev_0110_0084_…`; a client kind without `browser.host` cannot attach at all). The person's own activity in the view — a real key — moves control to them at once, on the Core and at the host, before any button (`before-input-event` → `SetBrowserControl USER`; the host's own CDP input is excluded); the agent's next input is `HUMAN_ACTIVE` and control has to be returned (`browser.spec.ts` preemption test). The emergency stop is host-owned as well as the Core's: the Browser panel's button fences the host's input for the session's life (`EMERGENCY_STOPPED`) and raises the Core's `EmergencyStop` (every new effect blocked, leases revoked, the reason on the log); any `EmergencyStopActivated` event fences the host too; a navigation is a reversible write of the session and is halted with the rest, observation continues; every host request is bounded on its own (settle 8 s, capture 7 s per attempt, click dispatch 1.5 s), independent of the model loop (`qual_ev_0085_…`, the faults E2E).

## Prompt-injection isolation

Page text, ARIA labels, DOM attributes, downloads and site-provided tools are untrusted evidence. Browser content cannot:
- change system policy;
- request hidden secrets;
- widen capabilities;
- approve effects;
- instruct the agent to ignore the user/system goal.

Context Compiler tags source and strips/segments browser content from trusted instruction channels.

As built (M7.7): three layers, none of which asks the model to be careful. **Tagging and marking** — every page-derived string is `UNTRUSTED_WEB_CONTENT` (M7.1), and every observation a tool returns (page state, entities, a file's text, a command's output, an issue) is scanned by `crates/browser::injection` for instruction-shaped passages (`OVERRIDE_INSTRUCTIONS`, `EXFILTRATE_SECRET`, `ASSUME_ROLE`, `HIDE_FROM_USER`; a short, explicit list, bounded excerpts); a hit is written onto the observation as `injection_suspected` (the content stays as data) and journaled as `SecurityEventRecorded {kind: PROMPT_INJECTION_SUSPECTED, tool, shapes, excerpt, action: MARKED}`; the system segment's rule 6 tells the model that tool content is data and that such passages are attacks to report. **No secret to give** — the Core spawns the terminal broker without any credential-bearing variable (`*_API_KEY`, `*_TOKEN`, `*_SECRET`, `PASSWORD`, …) and the broker strips them again for every child, so a command the content asks for finds nothing to print; a requested environment carrying one of the broker's own secrets is refused (`SECRET_IN_ENV`). **No secret leaves through a tool** — the pipeline compares every call's arguments against the credentials in the Core's custody (the provider keys the gateway can present, the forge token) and refuses a match before policy and before any effect, `SECRET_EXFILTRATION_BLOCKED`, naming the field and never the value; journaled as `SecurityEventRecorded {kind: SECRET_EXFILTRATION_BLOCKED, action: BLOCKED}`. Policy is untouched by content: a tool the page asks for that the surface withholds stays `TOOL_NOT_VISIBLE` / `TOOL_NOT_PROJECTED`, and no lease widens. The desktop card shows the count (`n blocked, m marked`). Proven on the real Core with a fake host (`qual_m7_7_…`: a hostile title, page text and README all marked with their shapes; `node -e` under `inherit_env` prints `key=unset`; the fill carrying the key is refused at `value` and never reaches the host; `forge.pr.create` stays unavailable; no request body or tool result or event carries the key; the task reaches review) and in the real app on a real hostile page (`browser.spec.ts`, E2E-016).

## Credentials

Login data is supplied only through an explicit user-approved credential broker. The model receives field handles/status, not password values. Browser Bridge can fill a credential handle directly into a bound origin/field under policy.

As built (M7.8): the broker is Electron main (`apps/desktop/src/main/credentials.ts`, `CredentialStore`): the person adds a credential in Settings — a label, an origin (exactly `scheme://host[:port]`), an account name and the secret — and the secret crosses main once, into `safeStorage` custody (ciphertext only on disk, owner-only; memory-only with a visible "held for this session only" when the OS offers no encryption). What comes back, and what the Core and the model ever see, is a handle (`cred_…`) with the label, the origin and the account name: the desktop registers them with the Core (`RegisterBrowserCredential` / `ForgetBrowserCredential`, `browser.host` commands only the desktop holds; memory-only on the Core, registered again on reconnect), `browser.snapshot` lists the handles bound to the page's origin under `credentials`, and `browser.act {ref, action: fill_credential, credential}` fills one: the Core resolves the field (`CREDENTIAL_TARGET_NOT_FIELD` for anything else), the handle (`CREDENTIAL_UNKNOWN`) and the binding (`CREDENTIAL_ORIGIN_MISMATCH` when the page's origin is not the handle's — nothing reaches the host) and sends the host `Act {credential_handle}` with no value; the host asks its store for the secret **for that page's origin only** and puts it into the real field through the same path a typed value takes; the answer carries `filled: true` and the handle, the log `BrowserCredentialFilled` (handle, origin, field, version, lease generation). A password field's accessible value is what the page exposes (masked), so no read returns the secret; the submission that follows is the protected action it always was. Proven on the real Core with a fake host (`qual_m7_8_…`: a headless client cannot register; a path is not an origin; the snapshot offers the handle; the unknown handle, the button and the other origin are refused before the host; the one fill the host sees names the handle and carries no value; the log has the fill by handle; a forgotten handle is gone) and in the real app (`browser.spec.ts` credential test: the credential added in Settings, the real password field holds the real secret before the approved sign-in, the site receives it in the POST, and no model text, browser log or settings text ever carries it).

## Verification

Actions can declare postconditions: URL/state fingerprint change, DOM/AX value, network response, downloaded artifact or screenshot region. Protected external actions require evidence before the Effect Ledger receipt closes.

As built (IMP-EV-0086/0147/0280, on M7.4): a visual fallback (a point click inside a captured region) is evidence only with its post-state verified — the completion verifier refuses `task.complete` with `VISUAL_FALLBACK_UNVERIFIED` while such a click declared no postcondition, or a failed one, and was not redone verified on the same reference (`qual_ev_0086_…`). Every browser record (`BrowserNavigated`, `BrowserPageObserved`, `BrowserActionPerformed`, `BrowserRegionCaptured`, `BrowserCredentialFilled`) names its tool call, so an artifact links through the call to its run, turn and arguments hash. What the session saw happen is offered back as evidence, never authority: `browser.act` records a `KnownTransition` (fingerprint before → reference, action → fingerprint after, URL, whether the postcondition held), `browser.snapshot` lists the transitions known from a page at the same fingerprint under `known_transitions`, a changed page (another fingerprint) is offered none, and the record is rebuilt from the log after a restart (`qual_ev_0280_…`).


## V2 media interaction

Browser screenshots/regions, uploaded screenshots and tool-returned images all use the same `MediaEnvelope`/Artifact Store path. Full-page screenshots are not the normal perception loop. Structural browser state remains primary; vision receives only targeted regions/pages when semantic state is insufficient, and any visual fallback records reason, source state version and post-action verification.
