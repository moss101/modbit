## Execution profiles

- `local_trusted` — runs against user-approved local workspace under host policy.
- `cloud_isolated` — runs inside tenant-bound isolated MicroVM.
- `review_isolated` — Isolated Non-Committing Reviewer profile (ADR-R-053, EPR-018). Processes run only inside a disposable review worktree: the canonical tracked tree is read-only, ephemeral writes are confined to that worktree, network and secret handles are denied by default, and Git commit/push, deploy and every external or persistent effect are refused. The process/tool budget is bounded and priced into the plan. The profile is realized by the same Execution Router on top of `local_trusted` or `cloud_isolated` isolation primitives and adds no broker or gateway; accept, cancel, timeout or crash kills its processes, revokes its handles and disposes the worktree. Trusted Core may export bounded evidence from the worktree through the existing artifact owner; the reviewer itself cannot persist anything.
- `review_isolated` as built (EPR-018): the broker confines every process of this profile with the host's real sandbox (macOS `sandbox-exec`: no network, writes only under the worktree and the temp dirs; Linux: a seccomp filter the broker installs by re-executing itself as the launcher — `socket(2)` refused for every family but `AF_UNIX`, `io_uring_setup(2)` refused, locked in with `no_new_privs`; no network, no user namespace needed; `AF_UNIX` stays open, so a local daemon with network of its own is reachable over its socket, as under a network namespace) and starts it with no inherited environment and no secret-looking variable; a host with no sandbox refuses the process (`SANDBOX_UNAVAILABLE`) and the Core admits no review environment there (`ProbeSandbox`). The Core provisions the disposable worktree, the review task and the confined lease (docs/27 "As built (EPR-018)").
- One execution interface, two adapters (IMP-EV-0109): the tools mean the same under every profile — the host's workspace and terminal broker serve `local_trusted`/`local_autonomous`, the task's sandbox serves `cloud_isolated` — with the same effect fields, the same refusals and the same events per call (`qual_ev_0109_…` compares one fixture on both); an adapter adds only its own identity (the sandbox's id, the host's workspace revision).
- `cloud_isolated` as built (M8.5): a task under it runs inside a sandbox the Sandbox Gateway issues for it when its run starts (`SandboxLeaseAcquired` on the task: the sandbox id, backend, isolation, the verified image's version, the guest's boot id, the workspace root inside — never a credential) and gives back when the task ends (`SandboxReleased`); its default lease is `fs.read`, `fs.write`, `git.read`, `shell.exec` under a `Destructive` ceiling. The tools with a sandbox path — `shell.exec`, `test.run`, `fs.read`, `fs.list`, `fs.stat` — keep their contract and act inside the guest through the `SandboxPort` the Core attaches to the task (a process runs in the guest with exactly the environment the call names, a read reads the guest's file); the tools without one (the change engine, git worktrees, search, the browser, the forge) are not compiled into the profile's surface. A worker's Core reaches the gateway through `ConfigureSandboxGateway` (URL, the worker's bearer token in memory, the cloud session lease generation the gateway checks); without a gateway a `cloud_isolated` run is refused `NO_SANDBOX_GATEWAY`. The change engine over the sandboxed workspace and verification inside it arrive with the handoff (M8.7).
- `plan` — plan mode (REQ-EV-0117, as built): a `READ_ONLY` ceiling and a lease of `fs.read` / `git.read`; no write, shell or worktree tool is compiled into its surface and the policy port refuses any non-read effect under it; the task's product is its recorded plan, reviewed like any candidate (docs/14 "As built (REQ-EV-0117)").
- Future profiles may be added through the same Execution Router; no tool changes required.

## Structured command contract

```text
ExecRequest {
  argv[]
  cwd
  env_handles[]
  timeout_ms
  pty: bool
  stdin_mode
  output_budget_bytes
  execution_profile
  capability_lease_id
  terminal_session_id?
}

ExecResult {
  process_id
  exit_code?
  signal?
  stdout_ref
  stderr_ref
  duration_ms
  terminal_cursor
  effect_receipt_id?
  checkpoint_before?
  checkpoint_after?
}
```

Shell-string convenience is parsed into an argv-aware request and clearly marked; internal deterministic tools prefer argv.

## Durable `modbit-execd`

A small broker owns local PTYs/processes and a bounded replay log. Core sends authenticated commands over local socket. UI can detach/reconnect without losing output. Core acknowledges output cursor; broker retains a sliding replay window and spills large output to OutputRef/object store. Broker is not authorized to create capabilities or decide policy. Processes started under `review_isolated` carry their review worktree and plan/leg IDs so cleanup and accounting are exact.

As built (M4.5): the broker outlives the Core (doc 33: durable terminal resources are detached, never killed). It writes an owner-only `execd.ready` in its data directory; a restarted Core reattaches through it instead of spawning a second broker, so a running command keeps running with the same handle and its output resumes from the cursor the run acknowledged (doc 51 E2E-008). Every session's metadata lives beside its log, so a broker that is itself killed (doc 54 fault 12) comes back knowing its sessions: those still running when it died are `LOST` — exit unknown, log replayable and sealed under an OutputRef — and a retry of the same request replays them rather than starting again. A Core holds one connection open for its lifetime; a broker with no Core connected past its orphan grace (`--orphan-grace-secs`, 60 by default) stops its processes as cancelled and exits. Attaches carry the terminal replay generation (doc 13; the Core's boot generation): an older reader is refused `STALE_GENERATION` and a newer one ends older attachments. Because the broker outlives the Core, it must inherit nothing from whoever spawned the Core: before spawning it the Core makes every handle it holds non-inheritable (Windows handle flags, Unix `FD_CLOEXEC`), so a supervising client waiting for the Core's pipes to close never waits for the broker's orphan grace instead; the broker's own stdin is null and its stderr is the profile's `execd/execd.log`. The Core records `TerminalCreated`, `TerminalOutputAdvanced` and `ProcessExited` on the task, and the protocol state (doc 19 layer 2) carries each handle with its last acknowledged cursor.

## Command failure semantics

Non-zero exit is a valid tool result. It emits `CommandExited` with status and output; Agent Runtime may inspect, repair and retry. `ToolCallFailed` means execution infrastructure/schema/policy failure. `TurnFailed` occurs only when runtime can no longer make progress under policy/budget.

## Sandbox substrate boundary

Cloud isolated execution uses a Modbit-owned Sandbox Gateway in front of the MicroVM substrate:
- authenticated tenant-bound sandbox lease;
- deny-by-default sandbox-to-internal network;
- explicit egress domains/ports by capability (as built, M8.6: enforced by the gateway's egress broker; the guest has no interface);
- dynamic credential handles via broker injection (as built, M8.6: the broker injects the secret it holds under the handle into requests to a credentialed virtual host);
- protected filesystem paths;
- typed guest RPC with task/turn/call/effect IDs;
- resource quotas and emergency stop;
- guest image is immutable/versioned and contains no tenant secrets.

As built (M8.3): the boundary is `crates/sandbox` (the canonical `sandbox-gateway-abstraction`): a `SandboxSpec` (tenant, session, task, the workspace source, protected paths, egress grants, resource bounds) compiles to a `CompiledPolicy` — substrate-side, whether the guest gets a network interface at all (none unless egress is granted) and the mounts; guest-side, the one writable tree (`/workspace`), the protected paths (the guest's control paths `/init`, `/etc`, `/proc`, `/sys`, `/dev`, `/run/modbit` always, plus the spec's under the workspace), the readable roots, the output, process and timeout bounds. A `SandboxBackend` boots `modbit-guest` under that policy and returns a private byte channel; `GuestLink` negotiates (the guest's hello — protocol version, methods; another major or a missing required method is refused before admission), admits it with a fresh 32-byte credential and the policy, and thereafter sends typed calls each signed with an HMAC over the call under that credential, verifying the signed replies; a call id is a nonce the guest answers once. Two backends: the MicroVM backend drives Firecracker over KVM through its API socket — the kernel and the immutable root image are the gateway's (the root is attached read-only; it is `modbit-guest` as `/init` over a static BusyBox userland, built by `tools/guest-image/build.sh`, no tenant data, no secret), the workspace is a per-sandbox ext4 image built from the workspace source and attached read-write, the channel is vsock; an egress grant is refused rather than served open (a tap device and a host firewall arrive with M8.6), so a guest has no network interface and the control plane is unreachable from inside. The reference backend runs the same guest as a child process on the host over loopback: it implements the whole contract so the conformance suite runs anywhere and isolates nothing — it says so (`isolated: false`) and a gateway serves it only when configured to. The conformance suite (`modbit_sandbox::conformance`) runs the same steps on both: negotiation, health, exec with exit code, stdin, timeout, timeout ceiling and output bound, the workspace present, write-then-read, a protected path, a path outside the workspace, a traversal and a control path refused, the control plane unreachable (asserted of an isolating backend), an unsigned and a replayed call refused, destroy twice. Proven on a real Firecracker MicroVM in the hosted `cloud` job and on the reference backend on every OS (`apps/sandbox-gateway/tests/gateway.rs`).

As built (M8.4, signed and versioned guest images): a publisher signs an `ImageManifest` (`modbit_sandbox::image`) — the image's SHA-256 and size, the guest version and protocol it carries, the kernel it was built for, its provenance — with an Ed25519 key (`guest-image-tool keygen | sign | verify`; the signing key never reaches a gateway). A gateway is configured with the publisher keys it trusts (`MODBIT_GUEST_IMAGE_KEYS`) and the signed manifest of its root image (`MODBIT_GUEST_IMAGE_MANIFEST`; the reference guest binary likewise, `MODBIT_GUEST_BIN_MANIFEST`): the MicroVM backend refuses to start (`IMAGE_UNVERIFIED`) unless the manifest verifies under a trusted key, the image on disk hashes to what it names and the kernel is the one it was built for, and it re-checks the image's hash before every boot; the guest that comes up must report the version and protocol the manifest names or it is refused at admission (`IMAGE_VERSION_MISMATCH`) before any credential is issued. Every sandbox the gateway issues names the verified image (`image: {kind, sha256, guest_version}`). The hosted `cloud` job mints a publisher key per run, signs the root image and the reference guest it built, and proves: the signed image boots and the guest is the one named; a manifest under another key, a tampered image and a manifest naming another guest version are refused — the last only after the guest said who it is.

## `modbit-guest`

Guest RPC methods are narrow: process start/wait/cancel, PTY attach/replay, file operations within mounted workspace, Git helpers, artifact upload/download, browser endpoint control and health. Gateway supplies a capability token scoped to sandbox lease and call.

As built (M8.3): `services/modbit-guest` — as `/init` of a MicroVM it mounts `/proc`, `/sys`, `/dev`, `/tmp`, `/run` and the workspace block device the kernel command line names at `/workspace`, sets the hostname and listens on the vsock port the command line names; as the reference backend's child it listens on loopback and maps `/workspace` onto a host directory. It speaks first (`GuestHello`: protocol 1.0, its version, its methods `health`, `exec`, `fs.read`, `fs.write`, `net.probe`, a boot id), accepts the gateway's admission (protocol check, the credential, the policy) and thereafter answers only calls whose HMAC verifies, each id once, each naming the task, the effect and the capability the body exercises (a mismatch is `BAD_CALL`); it enforces the admitted policy — a write only under the workspace and never on a protected path after resolving the symlinks it can, a read only under the workspace and the readable roots, an exec with exactly the environment the call names (nothing inherited), bounded output per stream, a timeout under the ceiling, a process count under the bound — and refuses the rest with a typed refusal (`UNAUTHENTICATED`, `REPLAYED`, `PROTECTED_PATH`, `OUTSIDE_WORKSPACE`, `LIMIT_EXCEEDED`, `BAD_CALL`). It mints nothing and fetches nothing. Git helpers, artifact transfer and browser endpoint discovery follow with M8.7 and M8.8.

As built (M8.5, guest protocol 1.1): followed processes — `proc.start` (argv, cwd, env, a timeout under the ceiling, optionally a PTY with a window and an open stdin) returns a process id; `proc.follow` returns the output after a cursor (up to a bound), waits up to a bound for more, and reports the exit, a timeout or a cancel; `proc.write` feeds stdin and may close it; `proc.cancel` kills; `pty.resize` changes the window. Every process keeps its output in a bounded ring (4 MiB) inside the guest with a cursor and a total, so a follower whose link was lost attaches again — the gateway relinks (`POST /v1/sandboxes/{id}/relink`: a fresh channel from the backend, admitted anew under a new credential, the guest's boot unchanged) — and replays from its cursor: nothing re-run, nothing lost, and a follower that fell behind the ring learns it (`truncated`). Directory operations — `fs.list`, `fs.stat`, `fs.mkdir`, `fs.remove`, `fs.rename` — under the same policy (the workspace root itself is never removable). A MicroVM guest also pins every existing protected path under the workspace read-only at the mount level at admission, so a process it runs cannot write them either; the reference backend enforces protected paths in its own file operations only, and says so. The required method set a gateway admits is `health`, `exec`, `fs.read`, `fs.write`, `net.probe`, `proc`, `pty`, `fs.dir`. Proven by the conformance suite on the MicroVM and the reference backend (`proc_replay_across_links`, `proc_stdin`, `proc_cancel`, `pty`, `fs_dir_ops`, `proc_protected_path_enforced`) and end to end by the cloud worker (`qual_m8_5_…`: a `cloud_isolated` task's `shell.exec` runs under the MicroVM's kernel and `fs.read` reads what it wrote).

As built (M8.8): `browser.start` (the guest's headless Chromium — `--chromium` on the reference backend, `/opt/chromium/chrome-headless-shell` in the image — with its DevTools on the guest's loopback, pointed at the egress proxy with the loopback bypass removed, or at a dead proxy when no egress is granted; idempotent), `browser.stop`, and `browser.forward`, after whose answer the link carries the DevTools bytes and nothing else — all under the `browser` capability, refused `POLICY_DENIED` unless the admitted policy grants a browser. A term (the reference backend's destroy, a drop) stops the browser before the guest exits; a MicroVM's dies with the VM. See docs/22 "Cloud browser".

As built (M8.6, the credential broker and egress policy): a guest never gets a network interface. What its policy grants leaves through the gateway's egress broker (`modbit_sandbox::egress`) on the host side of the sandbox's private channel: the guest runs a local HTTP proxy (a loopback port of its own, ephemeral — M8.8: several reference guests share a host — named in every process's `http_proxy`) when the admitted policy grants anything and points every process it runs at it (`http_proxy`/`https_proxy`, unless the call names its own); each client connection becomes one channel to the broker — over a second vsock port in a MicroVM, over a loopback listener of the sandbox's own on the reference backend — naming the destination. The broker decides by the compiled policy: an `EgressRule` (`host` exact or `*.suffix`, `port` or any, the capability that granted it) admits a `CONNECT` tunnel (TLS stays end to end between the process and the destination) or a plain-HTTP relay; a `CredentialGrant` (a handle, a virtual host, a target URL, a header and prefix, the capability) makes the broker perform the plain-HTTP request the guest sent against the real target over TLS with the secret it holds under the handle injected — the guest never sees the secret, the target or TLS; anything else is refused (`403` from the proxy). Every decision — admitted or refused, tunnel, HTTP or credentialed, with the capability — is on the audit (`sandbox_egress` in the store; `GET /v1/sandboxes/{id}/egress`). Secrets reach the broker with the provision (the Core's forge token under `secret.use`, crossing once, held in memory, never in the sandbox record, the log or the guest); the Core derives a `cloud_isolated` task's grants from its lease — `network.egress` admits the configured forge's API host, `secret.use` makes it a credentialed virtual host (`forge.modbit.internal`) — and journals the hosts on `SandboxLeaseAcquired`. Proven by the conformance steps `egress_allowed_http`, `egress_denied_http`, `egress_denied_tunnel`, `egress_credentialed`, `egress_secret_never_in_guest`, `egress_audited` on the MicroVM and the reference backend, and end to end by the cloud worker (`qual_m8_5_…`: a process in the guest reaches the forge through the broker with the token the guest never held, an ungranted destination is refused, both on the audit).

## Handoff local → cloud

Handoff bundle contains immutable workspace checkpoint, Git metadata, context/index generation references, task/protocol state, tool capability requirements and encrypted/opaque secret handle references. It never contains raw secret values. Cloud admission verifies capability parity before switching execution owner.

As built (M8.7, `ExportHandoff` in the local Core, `POST /v1/handoffs` in the Cloud API, `apps/cloud-worker/src/handoff.rs` in the worker): the local Core parks the task's run at its next safe boundary (`RunSuspended`; a running turn finishes first, a terminal task is refused `HANDOFF_STATE`), captures a checkpoint of the worktree (`CheckpointCommitted`, `before_handoff`) and writes the bundle to a directory: `events.jsonl` (the session's whole log, every envelope with its payload, as stored), `objects/<hash>` (every object the payloads reference, closed over — plans, self-reviews, outputs, the checkpoint manifest), `repo.bundle` (`git bundle --all`) and `manifest.json` (`kind: modbit-handoff`, the tenant, session and task, the goal and profile, the workspace root, the git head and branch, the checkpoint's id, manifest object and integrity hash, the object hashes, the `capabilities` the run's tools required, the `secret_handles` they used — `forge-token` under `secret.use`, a handle only — and `tools_used`). No secret value, no provider key, no token is in any part: the bundle is the log, the objects, the repository and the manifest, and the Core journals `TaskHandedOff {bundle_hash, checkpoint_id, git_head, capabilities, secret_handles}` behind it. The client uploads each part to the tenant's object store (`PUT /v1/objects`) and posts the manifest with the parts' hashes; the API refuses a capsule that would carry authority or a secret value (a grant or credential field in the manifest, a secret-shaped value in the manifest or the log — IMP-EV-0176) and verifies capability parity before the execution owner switches — a required capability `cloud_isolated` does not serve (`browser.control`, `git.worktree`) is `409 CAPABILITY_PARITY`, recorded on the command ledger — imports the log verbatim under the cloud tenant (the origin tenant stays on every envelope; a fork or a broken chain is `409`), stores the admitted manifest (the local one plus where its parts are, the admitting principal and the local manifest's hash; its hash is the `bundle_hash`), journals `TaskHandoffAdmitted {bundle_hash, from_tenant, capabilities}` and marks the session ready for a worker. The worker that claims the session materializes the continuation before it starts anything: it clones `repo.bundle` into a workspace of its own, checks the branch out, lays the checkpoint's files over it (the dirty edit is uncommitted, as it was), imports the objects into its Core (`ImportObjects`), rebinds the task there (`RebindTaskWorkspace {workspace_root, execution_profile: cloud_isolated}` → `TaskWorkspaceRebound`; the laptop's lease, valid under `local_trusted` only, is retired and `StartTask` grants the cloud profile's default one) and trusts the repository; `StartTask` then provisions the sandbox (`SandboxLeaseAcquired`) and resumes the run (`TaskResumed`, `RunResumed`) — the same transcript, the laptop's turns and tool results in front of the cloud model, the tools acting inside the sandbox. Proven end to end by `qual_m8_7_…` in `apps/cloud-worker/tests/cloud_worker.rs`: a local Core runs two turns of a task, the export parks it, the parity check refuses a bundle needing `browser.control`, the admission is replayed by `command_id`, and the cloud continuation reads the laptop's edit and the repository's history inside its sandbox and completes the task.

## Sandbox recovery

If a sandbox dies, Core marks in-flight tool calls unknown, reconciles protected effects, provisions a fresh sandbox, restores latest valid checkpoint and resumes. External side effects are never replayed automatically.

As built (M8.9, `services/modbit-core/src/sandboxes.rs` `recover_if_lost`, `checkpoint.rs`): a cloud task's worktree lives in its sandbox, so its checkpoints are taken there — at every turn boundary that ran a tool in the sandbox (`CheckpointCommitted`, reason `turn_boundary`) and before a completion or a handoff: the guest lists its `/workspace` hashed in one call (`fs.snapshot`; `.git` and symlinks skipped, bounded), the Core compares it with the seed the sandbox was provisioned from (the task's root on the worker), reads only what changed into objects and records what the seed had and the guest no longer has as deleted — the checkpoint is the guest's worktree relative to the seed. When a sandboxed tool call does not answer, the call's outcome is unknown (`ToolCallUnknownOutcome`, `SANDBOX_UNAVAILABLE`; docs/19 reconciliation, never a replay by the Core) and, before the model hears the result, the Core tries the link once (`relink`: a lost link over the same boot is re-admitted and nothing is lost — M8.5); a guest that cannot be reached again is lost: the gateway records the sandbox `LOST`, tears its remains down and answers `410 SANDBOX_GONE` from then on, the Core journals `SandboxLost`, provisions a fresh sandbox from the seed (`SandboxLeaseAcquired` again, a new id, the browser host re-attached when the task has one), writes the latest checkpoint's worktree into it (`write_file` / `remove` per path; `SandboxRestored {sandbox_id, replaced, checkpoint_id, epoch, files_written, files_removed}`) and tells the model, in the unknown call's result, what was restored and that what came after the checkpoint is its to redo; the run continues in the fresh sandbox — the tools find it at their next call. Proven end to end by `qual_m8_9_…` (`apps/cloud-worker/tests/cloud_worker.rs`): the sandbox's process is killed after the checkpointed turn; the call in flight is the one `ToolCallUnknownOutcome` on the log; `SandboxLost`, a second `SandboxLeaseAcquired`, `SandboxRestored` naming the checkpoint and both sandboxes; the gateway's record `LOST`; the model's retry reads the restored files in the fresh sandbox and the task reaches review. Not built: recovery of a sandbox lost while no call was in flight (the loss is detected at the next call); a checkpoint of a worktree beyond the bounds (20 000 files, 256 MiB of changes) is refused rather than half-taken.

## Environment revisions

The environment a run starts in is pinned to the run as one revision, and the run keeps it: a changed definition is a new revision the run does not drift into. A resumed run whose environment is not the revision it pinned waits for an explicit rebuild rather than continuing in an environment nobody chose.

As built (IMP-EV-0021 / IMP-EV-0062 / IMP-EV-0146, `crates/workspace/src/environment.rs`, `services/modbit-core/src/environment.rs`): the definition is three layers applied in order — user `<data>/environments/user.json`, team `<data>/environments/team.json`, repository `<root>/.modbit/environment.json` — each a JSON document `{extends: [blueprint…], toolchain: [{name, version_arg, optional}], env: {NAME: value}, path: [dir…], description}`; a blueprint is the same document by name in `<root>/.modbit/environments/<name>.json` or `<data>/environments/blueprints/<name>.json`, applied before the layer that extends it (a blueprint may extend blueprints; a cycle or a missing blueprint is a recorded problem, not a crash). A later layer's variable overrides an earlier one's, its `path` entries go in front (relative to the workspace root unless absolute), a toolchain entry of the same name is replaced. The revision captured at a run's start (`EnvironmentPinned {run_id, digest, revision_ref, sources: [{kind, path, sha256}], toolchain: [{name, version, optional}], path, env_names, problems}`) is the content digest of every source file by hash, every named tool's version as observed on the run's `PATH` (`""` = absent), the `PATH` entries, the variable names and values, the workspace root and the platform; the values live only in the object the event references (`revision_ref`), never on the log. A fresh run whose environment names a required tool that is absent parks needing attention (`ENVIRONMENT_UNAVAILABLE`) before any turn. The run's processes get the revision: `shell.exec`, `test.run` and `proc.exec` run with its variables under the call's own and its `path` entries in front of the host `PATH` (unless the call set `PATH`). A resumed run re-captures and compares digests: a difference is `EnvironmentStale {run_id, pinned_digest, current_digest, changes}` and the run parks needing attention (`ENVIRONMENT_STALE`, class Infrastructure, not retryable, the user action named) before any turn. The pin is keyed to the execution profile it was captured under: a resumed run whose profile has changed (a local→cloud handoff, a `RebindTaskWorkspace`) does not read the old profile's revision as stale — the environment legitimately changed with the profile, so the continuation re-pins what is there (the cloud run pins its sandbox's image, not the laptop's toolchain). `GetEnvironment {task_id}` → `EnvironmentView {pinned_digest, current_digest, stale, changes, sources, toolchain, path, env_names, problems, revision_ref}` shows the pinned revision (the current one when none is pinned) against what is there now; `RebuildEnvironment {task_id}` → `EnvironmentRebuilt {from_digest, to_digest, changes, offset}` re-captures and pins exactly what is there (idempotent: a second rebuild of the same environment records `from == to` and no change) and is refused `TASK_RUNNING` while a run is in progress on its revision — the run continues with `StartTask`, in the rebuilt revision. A `cloud_isolated` task's environment is its sandbox's: the revision is the verified image (backend, version) and the gateway's features; no host tool is probed. Proven by `qual_ev_0021_0062_0146_…` (`services/modbit-core/tests/surface_protocol.rs`): a repository layer extending a blueprint from the data directory; the run's process sees the repository's value over the blueprint's and the blueprint's directory on its `PATH`; the definition changed under the live run leaves the run in its revision and the view stale, naming the change; the Core killed and restarted, the resumed run journals `EnvironmentStale` and parks with `ENVIRONMENT_STALE` before asking the model anything; the rebuild pins the recomputed digest, the second rebuild changes nothing, and the run resumed after it sees the new value. Not built: a per-run override of the definition (the layers are the definition), and a rebuild from inside a run.
